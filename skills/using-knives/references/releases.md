# Release model, commands and evidence

Read before you plan, edit, cut, rebase, adopt or reap a release, or read membership or carriage output. Commands write locally and never push. The publish remote is the release remote when configured, else origin. Publish a new release name with `jj git push --remote <publish-remote> --bookmark <name>`. A release that the publish remote moves only forward (a fixed release branch) is pushed by the fast-forward rebase, then `adopt`, then a plain `git push`, never `jj git push`: see [Publishing](#publishing).

## Plan and keep the composition

`knives release [--repo REPO] [--consumer DIR]...` with no subcommand plans. It shows what a cut would hold, and whether parents still match branch tips. It shows branches missing or advanced past their released parent, members that carry prior release merges, and consumer pins. Options go before the subcommand: `knives release --consumer DIR include feat/x`.

- A release is a flat octopus merge, unless its series is stacked. Its direct parents are its members. Members reach the upstream base, which is never a direct parent. A member that merges upstream stays a member until an edit changes that. In a [stacked series](#stacked-series), a release is one merge of the previous release and its members. The previous release is the first parent, and it is never a member.
- `include` adds one parent. `drop` removes one. When no other member's history carries the dropped parent, `drop` says after the write whether the release lost that content, or that the parent left the parent set and the release's content did not change. `advance` moves members to branch tips. `rebase` moves the shared base, and refuses in a stacked series. `adopt` records a release that you finished by hand ([adopt](#knives-release-adopt-name---why-text)).
- Edits duplicate the release onto the new parent set and keep recorded conflict resolutions. The new composition can bring new conflicts. A cut goes ahead with such a conflict, exit `1`, and leaves it in the release for you: resolve it in the release in place, then run `knives release adopt <name>`. Where the conflict is at a file of a fix by hand that the gate holds, and the newest recorded write holds that conflict too, the cut names that fix as inconclusive at the file and goes ahead all the same. The conflicted write does not end the fix: a later cut or record that drops the fix is refused ([gates](#gates), 4). A cut from a conflicted write whose conflict the newest write resolved, as from a bookmark left at it, is refused, and the refusal gives the command that moves the release to the newest write.
- Every release write (`cut`, `cut --at`, `include`, `drop`, `advance`, `rebase`, `adopt` and `reap`) holds the fork's lock, `fork-locks/<upstream>.lock` beside `state.json`, from before it reads the ledger until its last write. The claim writers take the same lock ([coordination](coordination.md)). So two writes on one fork on one machine take turns, and the later one reads what the earlier one wrote: three `cut NAME --at REV` at once on one machine write one event. The lock orders the writes of one machine only. A write on another machine reads the event after its ledger pull. A write waits up to one minute for the lock. The plan and `members` take no lock.
- Every write (`cut`, `include`, `drop`, `advance`, `rebase`) resolves one kind of conflict itself. That is a `CHANGELOG.md` or `RELEASE_NOTES.md`, in any directory, where each side only inserted its own block at the conflicting place. The blocks the release already had go below the blocks the write brings in. The write writes the release's block last where the release inserted one there, and the members' blocks before it in jj's order, as in a first cut. At most places the write writes each block whole, byte for byte. It joins lists at one place only: in a file with one `## [Unreleased]` heading, inside that section, where every block that it writes there is plain `### ` lists. The write counts that heading in the whole file that it writes. A file with a second `## [Unreleased]` heading gets no join, so a join that knives wrote always reads as carried. A plain block is blank lines, then `### ` headings, each with list items, continuation lines that start with whitespace, and blank lines under it. It has no other heading, no code fence, no setext underline and no prose, and it ends with a newline. There each `### ` heading, such as `### Fixed`, has one target: its list in the last block that has that heading. The entries that another block puts under that heading go in the target's list, above the entries that the target already had. Entry lines stay byte for byte. The heading of a joined list and its blank lines are written once. So a first cut of three members, two that add `### Fixed` and one that adds `### Added`, writes `### Fixed` once, with the entries of both, and `### Added` once. A heading is the same heading only when its text is the same: a heading that differs by case or by a trailing space stays a list of its own. Where the place is not plain lists in a file's one `[Unreleased]` section, the write writes each block whole. It then prints one line for the file that names each `### ` heading that two of the blocks leave in one section (a heading that one block holds twice stays as that block wrote it, and is not named): ``CHANGELOG.md: left `### Fixed` twice: knives joins only plain `### ` lists in a file's one [Unreleased] section; join them by hand``. Join those lists by hand and record it with `adopt --why`. The output names each such file with the first line of each block, and the ledger event ends with `; union: <files>`.
- After every write (`cut`, `cut --at`, `include`, `drop`, `advance`, `rebase`) and every `adopt`, knives reads each `CHANGELOG.md` and `RELEASE_NOTES.md` in the release's tree, whether the command changed it or not. It skips a file that is still conflicted and a file with no single `## [Unreleased]` heading. For each `### ` heading that the `[Unreleased]` section holds more than once, it prints one line, once for each file and heading: ``CHANGELOG.md: [Unreleased] holds `### Added` twice; knives changed no line for it; join them by hand before you push``. The line also names a heading that the left-twice line names. A heading is the same only when its text is the same, and a `### ` line in a code fence is no heading. knives changes no byte for it. A clean merge can leave such a heading: a member's own new `### Added` block above the release's `### Added` list merges with no conflict. Join the lists by hand and record it with `adopt --why`.
- knives never renumbers. Two blocks that claim one version stay as their members wrote them. Renumber by hand and record it with `adopt --why`. Every other conflict is yours: a release log where a side changed or removed lines another side kept, a release log where a side inserted a block with no final newline and something else would follow it, and every other file. Resolve it in the release in place, then run `knives release adopt <name>`.
- The write unions a block with no final newline only where it ends the file. Anywhere else, its last line would run into the next line. The write never adds a byte to keep them apart, so it leaves that conflict to you.
- The cut audit, `members --verify` and `--carries` for a member of a release read a member's block that such a union holds as carried. A member is carried where the release holds its whole block, byte for byte, anywhere in the file, as before. A member whose block is plain `### ` lists is also carried where the release's one `[Unreleased]` section holds each of its entries under the same `### ` heading, byte for byte, outside a code fence. That line can be another member's or the release's own: a line that another member or the release also holds counts. A single line in a released section, such as `## [1.0.0]`, counts only as part of the member's whole block. A release with no `## [Unreleased]` heading or with two holds no joined entry. So a release whose `[Unreleased]` lost a member's entry reads that member as missing, unless the release holds the member's whole block elsewhere in the file, or holds each of its entries under the same heading in `[Unreleased]`, from another member or from the release.
- A **fast-forward carrier** is a parent that is an earlier write of the same release name. The fast-forward rebase in [Publishing](#publishing) adds one. A parent is a carrier when the ledger records it as a cut or edit of the name, when it is the publish remote's commit of the name, when it is a visible rewrite of either, when a recorded cut or edit event of the name names its change id (a pushed copy keeps its write's change id), or when a recorded event of the name lists it with the label `<name> earlier write (carrier, not a member)`. A carrier is never a member.
- The plan and `members` label a carrier `<name> earlier write (carrier, not a member)` and do not count it as stacked. The cut's carried rows do not name it. `adopt` records it.
- In the ledger, only `adopt`'s record of the fast-forward parent that it took writes that label. It never writes it for a member of the write that it replaces. The label is the only record of a carrier that no event records as a write, such as a published resolution that you squashed into the release ([the squash remedy](#knives-release-adopt-name---why-text)). `adopt` reads such a parent as a carrier only while the publish ref names it. So push in the order that [Publishing](#publishing) gives: the fast-forward rebase, `adopt`, then a plain `git push`. A push before that `adopt` (in the squash remedy, the second `adopt`) leaves the carrier unlabelled. The next write then takes it for a member, stacked on a prior merge.
- Every write that composes from the release's parents (`include`, `drop`, `advance`, `cut`, `rebase`) leaves the carriers out. It first writes the release again on its other parents with the release's own tree. So a resolution that you made over the carrier becomes the release's own change and carries forward. Each push adds one carrier, and the next write leaves it out, so carriers do not pile up.
- Keep stated cross-fork dependencies. A dependent without its requirement ships a release that cannot work.

### One branch is member and PR head

- The branch forks from the shared release base and is linear past it. In a [stacked series](#stacked-series), it can also be built on the previous release, and it is linear past that release. A rebase onto newer upstream is intentional, for example when a maintainer asks. It is never a side effect of starting work.
- `release advance` follows the change id as well as ancestry. To move the whole composition, use `release rebase`. The fork point of a member alone is not a finding.
- Never make a second "release-lineage" or "sibling" branch with the same PR content on an older base. If it cannot compose, rebase the release. Do not split review and conflict work across two copies.

### Raw rebase and retained releases

`advance` and `rebase` change only the release in hand. A raw `jj rebase -b`, `-s` or `-r` can reach older release/keep merges. Those still pin member commits for consumers or for conflict evidence. Before a rebase by hand, run the bidirectional gate from **fork-work** (§7):

1. Is the branch a parent of any release/keep merge?
2. Does it descend from any release/keep merge?

Bare `release members` answers neither for older releases. It sees only the current composition. Name a release to see its parents. Keep published merge commit ids.

- A member must carry no merge past known trunk positions: `<trunk>@upstream`, `<trunk>@origin` and local trunk. A branch built on a release merge carries all parents of that merge. In a [stacked series](#stacked-series), knives measures past those positions and the previous release of the release in hand. So a branch built on that release carries no merge of it, and it is linear.
- `include`, `advance` and the first `cut` refuse such `stacked-history`. Planning reports existing stacked members. A merge that a trunk position reaches belongs to trunk. If every local view lags the branch base, the detail says that these can be upstream merges. `sync` fetches them.
- The exception: a merge whose side parents (every parent after the first) the release's other members already carry, and that is no release cut: no release ref names it, and the ledger records no knives write of a release with its change id. The branch then brings only its own line (`git rev-list <branch> ^<release>`). `include` takes a branch that merges the members it descends from, one or several, beside them, which stay members. A branch the last event recorded as one of those members continues that member: a named `advance` replaces it and keeps the members it merged. Both name the merge. The plan measures each member against the others and notes it, and names the verb that takes each branch. A bare `advance` leaves such a branch alone. A merge whose side parent the release lacks still refuses, and the refusal lists every commit the branch would bring. So does a branch that merged its own earlier tip back in.
- After that merge was pushed anywhere, `jj rebase -b <branch> -d <trunk>` is not the remedy, because it rewrites the merge. Rebase only the branch's own commits, from the ref that the gate found:

```text
jj rebase -s '<release-or-keep-ref>..<branch>' -d <trunk>@upstream
```

- This keeps the change ids for `advance` and keeps the merge id. `-b` avoids this hazard only when the merge was never pushed. The other direction of the check still applies.
- When a released parent merges upstream and its branch continues, ancestry cannot identify it, because every new trunk branch descends from it. The cut/edit record names the member. Planning offers `advance <branch>`, or `rebase` to retire the parent. `include` refuses a second copy. A named advance says when its match rests on the record alone.
- A cut carries exactly what its parents hold. The plan says `N parent(s), flat` only when no member carries a prior release merge. Otherwise it counts the stacked members. In a stacked series, N counts the previous release too, and a member that is built only on the previous release is not stacked.

## Names and consumer gates

- **Dated scheme** (no `release_branch`): a name is `release/YYYY-MM-DD`, `release/YYYY-MM-DD.N` (N is one or more digits, never `.N.M`) or `release/YYYY-MM-DD-<label>` (one or more characters, no `/`). git must be able to hold the name as a ref: no space, `~`, `^`, `:`, `?`, `*`, `[`, `\`, `..`, `@{` or control character, and no final `.` or `.lock`. Such a name has no place in the order, and every cut refuses it. Make a name only with `release cut NAME`, when the pin gate needs a new name. Never make a release bookmark by hand and then advance it.
- **One order for each series.** A name sorts by its date, then by the rest of the name in version order, then by that rest as bytes. In version order a run of digits compares as a number and any other run compares as bytes, run by run; a digit run sorts before any other run; and a name that starts another sorts first. So `-speed-8.0.9` < `-speed-8.0.10` < `-speed-8.1` < `-speed-8.1.1`, and `-speed-7.1.1.2-baseline` < `-speed-7.1.9` < `-speed-7.1.10`. A `.N` name sorts after each `-<label>` of its date, because `-` sorts before `.`. A later name on one date supersedes an earlier one, and the reap keeps only the newest. A name the series cannot read, such as `release/9.2/foo`, has no place in the order: `release cut` refuses it as a usage error (exit `2`) and gives the grammar, it is never the newest release, and the reap never takes it.
- **Named series** (`[repos.<name>.series.<series>]`): one dated line per base. The default series is the entry's own `base` with `release/YYYY-MM-DD[.N|-<label>]` cuts. Series `<series>` cuts `release/<series>/YYYY-MM-DD[.N|-<label>]` on its own base.
  - Every release verb takes `--series <series>` (`knives release --series 9.2 cut release/9.2/2026-10-20`). It then sees only that series' cuts, base, ledger baseline, reap set and consumer pins (`refs/heads/release/<series>/*`). Without it, the verb acts on the default series.
  - A branch belongs to the series whose base it forks from latest. The first cut composes only that series' branches, and the plan lists only them. `include` or `advance` of a branch from another series is refused, naming the series it fits.
  - A branch that fits no series is refused, with one of two reasons. It forks from two bases at the same point. When one base is an ancestor of another, every branch at or below the older base's tip ties. Or it has no single fork point with some base (criss-cross).
  - Every series' base must resolve. If a declared base does not, every release verb exits `3` and names it (`fetch it, or set the series' base_remote`). It never assigns that series' branches to another.
  - A cut name equal to a series' prefix (`release/9.2`) is refused, because git cannot hold it beside `release/9.2/<date>`.
  - `status` and `repos` show only the default series' newest cut. Read a named series through `knives release --series <series>`. `audit` checks drift for every series' cuts and notes each branch that fits no series.
  - `stacked = true` on a series table builds each release of the series on the one before it ([stacked series](#stacked-series)). The default series is never stacked.
- **Fixed scheme** (`release_branch = "<name>"`): cuts move that branch in place, through the jj allow-backwards mechanism. `release cut` takes no name, and a dated name is refused. The cut uses the local composition, including unpushed edits.
- Under the fixed scheme, release verbs read the published position from the local `<name>@<publish-remote>` tracking bookmark, not the live remote. Fetch first when freshness matters. `consumers` and `pushed` read the live remote.
- Every plan, cut and edit reads registered `consumers` and `--consumer <DIR>` scans. With neither, no pin is known. The plan says so and treats the release as unpinned, and verbs continue. An install-based consumer can have no lockfile to register.
- An unreadable consumer that is configured or passed is a problem and blocks the verbs. So does a shared ledger that the plan could not pull, because the drop guard would check a stale cut ([ledger](ledger.md#sharing-between-machines)).

`include`, `drop`, `advance` and `rebase` refuse with exit `3` in these cases:

- Every pin **of this release** is frozen on a revision, so an in-place edit reaches nobody. Under the dated scheme, make a new dated name. Under the fixed scheme, the refusal says to update the frozen pins or change the scheme, because a fixed branch cannot reach revision pins.
- Pins frozen on older releases do not block. A release with no pins is free to edit. A pin is of this release when it names the branch, or freezes the commit that the publish remote holds (a lock `?rev=<sha>` or `#<sha>`).
- Upstream trunk does not resolve, so base and members cannot be told apart. Fetch upstream first.
- The release in hand is unrecorded: you changed it by hand, and no `adopt` recorded it. See [Adopt a hand resolution before the next write](#adopt-a-hand-resolution-before-the-next-write).
- Every parent of the release in hand is a carrier, so the release has no member to compose. The refusal prints the remedy that `adopt` prints ([adopt](#knives-release-adopt-name---why-text)).
- In a [stacked series](#stacked-series), `rebase` always refuses, and `drop` refuses the previous release.

## Stacked series

Set `stacked = true` on a series table ([configuration](configuration.md)) when each release of the series builds on the previous release. An example is a frozen version line, such as a `9.2` line on the fork: each new 9.2 release adds members to the last one and never composes again from the trunk. Without the key, every rule in this file applies as written. The first cut of a stacked series has no previous release, so it is a flat cut of its branches.

Below, C is a release of the series, and P is its previous release.

- **The reading.** knives reads C along its first-parent line, down to the trunk. P is the nearest commit on that line that a cut or edit event of the series records as its write or labels as its previous release (see **The ledger event** below). The reap after a stacked cut forgets every ref of P. So for a P cut by hand, with no recorded write, that label is all that names it. With no such event, P is the nearest commit on the line that a release ref of the series names, locally, on the publish remote or on origin. Tags do not count. The members are the side parents (every parent but the first) of each merge from C down to P. So a cut of `[P, D, M6, M5]` and the chain `merge(merge(merge(P, D), M6), M5)` read alike: P, then D, M6 and M5.
- **A commit with one parent between C and P** has no member that explains its change. The plan and `members` report a problem and exit `3`, and every write refuses C. Each names that commit.
- **The cut.** `cut NAME` starts NAME as one commit on P, with P's tree. That start is identical to P. So the cut goes ahead only when P is published (a tag or a `record: published` note names its commit) or every pin of P is frozen ([identical-cut exceptions](#identical-cut-exceptions)). It then says that NAME `starts identical to` P and is the composition to edit. Otherwise it refuses, exit `3`, says `nothing to cut`, and tells you to `include` into P itself. After the cut, `include` adds each member.
- **Members can stack on P.** `include`, `advance` and the plan measure a branch's merges past the trunk positions and P. A branch built on P is linear past them, so it is no `stacked-history`. A branch that carries a merge past them is refused, as in every series. Before the next cut, the plan names each branch built on the release in hand as one that the next cut includes.
- **P is never a member.** The plan and `members` show P on a row of its own: `<P> previous release (not a member)`. `drop` of P refuses, exit `3`. `advance` never moves P. `rebase` refuses, exit `3`: each release is built on P, so there is no base to move. The stale-parent checks report neither P nor a merge between C and P.
- **The audit.** The cut audit and `members --verify` replay each member from its fork point with P, not with the trunk. They do not replay P. The check for unexplained files reads the files that changed between P and the release.
- **The composition gate** takes P as the base. A recorded member passes when P carries it. The gate also holds the newest recorded write of the newest release that the ledger records in the series ([gates](#gates), 4). That write, or a commit that stands for it, must be on the first-parent line of the commit the subject starts on, that commit included: the previous release a cut starts on, or REV for [`cut NAME --at REV`](#knives-release-cut-name---at-rev). A commit stands for the write when it is a successor of the write in jj's operation log (what jj leaves when it rebases the release over a member rewritten in place), or when it has the write's tree, whatever its change id (a fast-forward copy, or a `jj duplicate` of the write, which has a new change id). A commit that only shares the write's change id does not stand for it. For example, the edit that an `adopt` replaced keeps the adopt's change id, but it does not have the adopt's fix. The check walks down the line and stops at the first commit that is an ancestor of the write. Below that commit, a commit with the write's tree does not stand for it: a stacked start has the tree of the release it starts on. Past the commits that descend from the write, the check also stops at the first commit that the trunk reaches. So the subject carries that release and every release below it. Otherwise the gate refuses, exit `3`, and names the write, whether it is a cut or an edit, its commit and its release. A cut that starts on an older release, for example on a machine whose refs stop below the newest recorded release, or that has no release ref at all and reads as a first cut, is told to fetch, then move that release to the write, with the `jj bookmark set` command. A record is told to build REV on the write. Where this repository does not hold the write, the gate does not walk the line: it refuses because it cannot hold the subject against that write ([gates](#gates), 5), and a record is told to fetch, then build REV on the write, or, if the fetch does not bring the write, to run `knives release adopt <release>`. `--allow-drop` states the drop instead: the subject goes ahead, its `--allow-drop:` line names the write, its release and its commit, and its event records `; not built on <release>'s newest recorded write (a cut) <commit>`. This line check is about releases, not fixes by hand. An adopt on the subject's line carries nothing for its fix: the subject's own tree must carry each file of the fix that the gate holds ([gates](#gates), 4), as the subject's own merge can undo the fix.
- **The ledger event.** Each cut, edit and `adopt` event records P after the commit in its evidence. It records P first in its `parents`, labelled `<P> previous release (not a member)`. The members that it records are the reading's members, never the commit's literal parents. Every reader of recorded members skips the labelled P.
- **`adopt`** measures a hand resolution against the merge of P and the members, with the release-log union. It counts only the members' lines: each member's added lines are measured from its fork point with P. So a member's deletion of P's lines is no lost line ([adopt](#knives-release-adopt-name---why-text)).
- **The orphan gate** does not run. A stacked cut keeps P as its first parent, and the reap abandons nothing that the cut descends from. So the cut strands no commit, and it needs no `--allow-drop`.
- **The reap** forgets a superseded name that the live release descends from, and keeps its commit ([reap](#knives-release-reap)).
- **A release made outside knives**, a chain of merges included, is recorded with [`cut NAME --at REV`](#knives-release-cut-name---at-rev). An edit measures the release's own change against the merge of P and its members, not against its literal parents. So an edit of a chain keeps what each inner merge resolved, and so does the check that reads the release as recorded once jj rebases it over a member rewritten in place.

## `knives release cut [NAME] [--allow-drop]`

- A normal cut carries the composition in hand: previous parents **verbatim by commit id**, even if a member bookmark is now divergent. It adds no branches and advances no members. Only the first cut, with no composition, starts from every branch. A cut in a [stacked series](#stacked-series) starts as one commit on the previous release instead.
- The cut audits the candidate first. The net diff of each member, from the members' fork point with upstream trunk, must be in the cut tree. In a stacked series, each member is measured from its fork point with the previous release. Divergence that the release in hand already has is carried forward: `diverges where the release in hand (a recorded write) already does; carried forward`.
- The cut refuses an unrecorded release in hand, exit `3`, and writes nothing, whatever its audit would say ([below](#adopt-a-hand-resolution-before-the-next-write)). So the divergence it carries forward is a resolution that knives wrote or `adopt` recorded, a release that knives could not check, or a release whose name has no recorded write at all. For a release that knives could not check, the carried rows say `diverges where the unrecorded in-hand release already does`, and say to record it with `knives release adopt` and cut again ([unchecked](#when-knives-cannot-check-the-release-in-hand)). For a release whose name has no recorded write at all, the carried rows say `the ledger records no write of the release in hand, so nothing measured its divergence from this member; check that divergence by hand`. Nothing recorded or measured that divergence, and `adopt` refuses a release with no recorded write, so check each such member's divergence yourself. The cut is still written, with the exit it would have without the rows. It also prints the unchecked line and marks its event `; unchecked: no record` ([unchecked](#when-knives-cannot-check-the-release-in-hand)). `knives release adopt <new name>` records the new name, and the cut after that carries the divergence forward as a recorded write's.
- A failed audit writes no cut. A pass makes and names the release in one operation, except for the fixed recording path below and for `--at`, which records a release cut outside knives and makes no commit ([`cut NAME --at REV`](#knives-release-cut-name---at-rev)).
- A cut lists a workspace to remove only when the ledger names its branch, no bookmark of that branch is left locally or on any remote, and no live claim holds it. It never lists the default workspace, a workspace knives did not make, or a `knives start` workspace whose release a reap forgot.

### Gates

1. A dated name must sort after the newest release of the series, in the one order above. A reused name, an older date, an older suffix or an older version is refused before the build, exit `3`, because reap keeps only the newest name. A name the series cannot read is refused earlier, as a usage error (exit `2`), with the grammar. So is a name that git cannot hold as a ref, such as `release/2026-08-04-x~1`: the refusal names the rule it breaks.
2. The orphan gate refuses to strand commits that only the previous lineage reaches. `--allow-drop` states the intended exception. After the reap, the cut says what it dropped: a commit it does not carry counts as dropped only when it is no longer visible. Such commits rest on the previous cut, so the reap usually keeps that cut and drops nothing. A stacked cut runs no orphan gate: it keeps the previous release as its first parent, and its reap abandons nothing that it descends from.
3. Before the content audit, knives compares the candidate with the previous published cut. The **same tree and parents** is refused as identical, exit `3`, except as below. New members come through `include`, new tips through `advance`, and a new base through `rebase`, not through a new name. A stacked cut always starts identical to the previous release, so it has its own gate before the build ([stacked series](#stacked-series)).
4. The composition gate reads two ledger events, which survive a moved bookmark: the event of the previous cut, and the newest recorded write of the newest release that the ledger records a cut or edit of in the series. On a fixed branch, that release is the branch. It is the release in hand, unless this machine has not fetched a newer cut that the ledger records. That write is the release's cut, its newest edit or an `adopt`, whichever the ledger records last. This repository must hold that write: where it does not, nothing here can tell what the write carries, and the gate refuses (5). A member that either event records is a recorded member, and it counts once. A member of the previous cut whose change id a member of the newest write has is superseded by that member, as `advance` recorded it, and only the newest write's member is held. Each recorded member must be a parent or an ancestor of a member or the base. Otherwise it needs a reachable rewrite that stands for it (a successor of it in jj's operation log, or a commit with its tree), a commit with exactly its tree reachable from a parent (a history recreated outside jj; the cut names the twin), or its net diff in the candidate tree. An older version of the member, which only shares its change id and no recorded write names, is no such rewrite. A member that came through upstream base passes. In a stacked series, the base is the previous release, so a recorded member that it carries passes, and the newest write, or a commit that stands for it, must be on the first-parent line of that previous release, the release included ([stacked series](#stacked-series)). The gate also holds each fix by hand (files resolved by hand or changed beyond its baseline's conflicts) that an `adopt` of any release of the series recorded, before or after that release's cut. It holds each file of a fix on its own, against the file's reference: the newest recorded write of the series, the newest release first, that holds the file with no conflict. A knives write that leaves the file with conflict markers is no reference. It does not end the hold on the file, and a subject is not held to its content there. So after an `advance`, an `include` or a cut that leaves a fixed file conflicted, the fix stays held, and a later cut or record that drops the fix is refused. To keep other content at that file, resolve the conflict in place and run `adopt` ([adopt](#knives-release-adopt-name---why-text)). The fix is the adopt's change against the baseline that `adopt` measured it against: the write it replaced, rebuilt on the adopt's members, or an automerge of them. The files of a fix are the files of its event's `fix_files` list ([ledger](ledger.md#automatic-entries)) and, where this repository can measure the fix, the files that the adopt's change changes. This repository cannot measure a fix where it does not hold the adopt's commit, or where the series cannot read that commit as a release. An event that an older knives wrote names its files in its text alone. The text joins the paths with `, ` and ends a list at `; ` or ` (why: `, so a path that holds one of those reads back in pieces. The paths of such an event are each path that its text may name, each run of up to 16 of its pieces joined back with the separators between them. Where this repository can measure the fix, such a path is a file of the fix only where the adopt's own tree holds it, beside the files that the adopt's change changes: a piece such as `y.txt` of `x, y.txt` is none. Where it cannot measure the fix, each such path is a file of the fix, so the gate can hold more than the fix. There, such a text may not read whole, in two ways. A list that has more than 16 pieces may name a path that holds more than 15 separators, which the text does not give. And the text after `resolved by hand: ` may hold a part that `adopt` writes after that list, once or more: `; changed beyond the baseline's conflicts: `, `; why: `, `; carriers: ` or `; added lines absent: `. A path and a reason are free text, so the list may end at that part or name a path that holds it. Such a text reads two ways, and the reading that ends the list there may name fewer files. Either way, this repository cannot read the files of that fix whole, and the gate refuses every cut and record, whatever it holds (5). A clone that can measure the fix reads its files from the adopt's change, so it reads such an event as before. The list of files changed beyond the conflicts ends at its last ` (why: `, so it reads at least whole. The `fix_files` list of a newer event reads whole. A string that is no repository path, as a peer's ledger may carry, is no file of the fix. A deletion is content: where the fix deleted a file, the absence of the file is the fix there. The hold on a file lasts while its reference still holds the adopt's content there: the adopt's change at that file replays empty onto the reference, or the reference holds what the adopt holds at a file that the change leaves out, which includes nothing at both. So the hold on a file that the fix deleted ends only where its reference holds the file again. For a fix that this repository cannot measure, each file of the fix is held to what its reference holds there. A reference that holds nothing at the file holds the fix there as an absence, and that hold ends only where a later reference holds the file again. So a fix that the later cuts and edits kept is held at every later release. Where this repository can measure the fix, a later write that removes the fix from a file, or changes the fix's lines there again, such as a later adopt, ends the hold on that file alone, and the other files of the fix stay held. `--allow-drop` lets a cut or a record go without the fix. Where this repository does not hold the newest write, no fix is held, and the gate refuses for that write. The subject carries a held file when the adopt's change at that file replays empty onto it, where this repository can measure the fix. So a member that changes other lines of a file whose lines the fix changed costs the fix nothing. A file that the fix added has no other lines: its replay onto other content there conflicts. At a file that the baseline left conflicted, the replay asks for the adopt's resolution. Otherwise the subject carries the file when it holds exactly what the file's reference holds there, which includes nothing at both. So a subject that holds a file that the fix deleted lacks the fix. A knives cut whose candidate leaves a held file conflicted, where the newest recorded write holds that conflict too, cannot answer there, as for a member whose replay conflicts: the cut goes ahead, exit `1`, with the conflict, and names the fix as `<fix>, in <n> file(s): <files>: carry check inconclusive (the cut leaves those files conflicted; resolve them in place, then run `knives release adopt`)`, and its event lists it after `; unverified: `. Resolve the file in place and adopt it. A cut that leaves a held file conflicted where the newest write holds no conflict there, as from a bookmark left at a conflicted write that a later adopt resolved, lacks the fix and is refused, and the refusal gives the command that moves the release to the newest write. Where a write that this repository does not hold comes before any reference of a file, only the replay can carry that file. Only the subject's own tree counts: the candidate of a cut, REV of a record. An adopt on the subject's first-parent line carries nothing for its fix, as the subject's own merge can undo it. A fix is no member's content, so the audit's check for unexplained files leaves each file that this gate holds to this gate, and only those files: no member explains them, and the audit does not report them. A subject that lacks a fix at a file is refused once, by this gate, naming the adopt and each such file.
5. A missing member refuses the cut, however it was lost: a merge rebuilt by hand, a moved bookmark, a `drop` since the last cut, or a release bookmark that is older than an `include` since the last cut (for example, on a machine that did not fetch the edit). A recorded commit that does not resolve counts as dropped. So does the newest write itself: where this repository does not hold it, the cut is refused, exit `3`, and the refusal reads `this cut cannot be held against <release>'s newest recorded write (a cut) <commit>: this repository does not hold that commit, so it cannot tell what that write carries`. The gate never holds such a cut to less. The refusal names each member with the event that records it. A member of the previous cut reads `the previous cut <name> recorded <n> member(s) this cut does not carry`. A member that only the newest write records reads `this cut does not carry <n> member(s) which <release>'s newest recorded write (an edit) holds`. A missing fix by hand refuses the cut too, exit `3`, and reads `this cut does not carry the fix by hand of <release>'s adopt <commit>, in <n> file(s): <files>`, one line for each adopt, with the files that the cut lacks. For a fix that this repository cannot measure, the line adds why and what held the fix: ` (this repository does not hold <commit>, so the fix is held by its content: what <release>'s newest recorded write (a cut) <commit> holds in those files)`. Where the newest write is not the reference of each of those files, as where it leaves one conflicted, the line names the reference of each file instead: ` (…, so the fix is held by its content: what the newest recorded write that holds each file with no conflict holds there: <file> at <commit>)`, and `<file> at none here` where no write that this repository can read is the reference. A fix whose files this repository cannot read whole (4) refuses the cut whatever it holds, exit `3`, and reads `this cut cannot be held against the fix by hand of <release>'s adopt <commit>: this repository does not hold <commit>, and the adopt's event is an older one that names the files of the fix in its text alone, in a list of more than 16 pieces, which may name a path of more pieces than this repository reads`. For a list of files resolved by hand that another part follows, so that the list reads two ways, the end reads ``in a list that `; why: ` follows, which may end there or name a path that holds it``, with the part that it found. Where this repository holds the adopt but cannot read it as a release of the series, the line says `this repository cannot read <commit> as a release of the series` instead. The last line gives the remedy. For a member of the previous cut, `knives release include <branch>` restores it. For a member that only the newest write holds, for a fix, or for a newest write that this repository does not hold, fetch, then move the release to that write: `jj bookmark set <release> -r <commit> --allow-backwards`. The release here is older than that write, and an `include` on it would write a second write of the release beside that write. Where a fix needs another write that this repository does not hold, the fetch names the remote and the branch or tag that has it now: `fetch <remote>'s <ref>, which holds <commit>, then move …`. That write is the adopt of a fix whose files this repository cannot read whole, or the write where the walk for the reference of a file that the cut lacks stopped. For such a refusal alone, knives reads the branches and tags of origin, and of the publish remote where it is another remote, once each, with `git ls-remote`, and names a fetch only where one of them has a ref at that commit, matched by its full id or by the start of it that the ledger gives. A fetch does not bring a write that no remote holds, as when git refused its push after `adopt` recorded it ([publishing](#publishing)), or when an edit abandoned it and a later write moved the ref that held it. Where no remote has such a write, no fetch is named for it: a file whose reference walk stopped there then counts as a file with no reference, and the adopt remedy below stays the way on; the adopt of a fix whose files this repository cannot read whole leaves that fix with no step, as below. Where a remote cannot be read, the last line ends `; <remote> could not be read`. So for a newest write that this repository does not hold, the last line also says that, if the fetch does not bring that commit, `knives release adopt <release>` records the commit that this repository holds as the release's newest write. For a fix that names its files, the last line also says how to keep the new content of its files instead: edit the release of the newest write by hand to hold that content, and run `knives release adopt <release>` for it. That adopt then holds those files. A fix whose files this repository cannot read whole gets no step where no fetch and no cut meets it: where this repository holds its adopt but cannot read it as a release, and where this repository does not hold the adopt and no remote that knives read has a branch or tag at it. The last line gives the remedies of the other findings, if any, then ends `re-run with --allow-drop to state the drop is intended: nothing in this repository can hold a release against the fix by hand of <release>'s adopt <commit>`, after `then` where remedies come before it. For an adopt that this repository does not hold, it adds why, and names only the remotes that knives read: `, as <remote> has no branch or tag at <commit>` where it read one, `, as neither origin nor <publish remote> has a branch or tag at <commit>` where it read both, and `, as no remote could be read for a branch or tag at <commit>` where it read none. Where a remote has the adopt of a fix whose files this repository cannot read whole, the last line names that fetch first, before `include`. Where the refusal holds such a fix, whatever its remedy, the last line then ends `; --allow-drop is the last resort: it also waives the checks of each recorded member, of the newest recorded write, of each other fix by hand and of the commits reachable only from the previous release`. `--allow-drop` goes past that fix only by going past those checks too, the member checks included. So fetch the adopt first, where a remote has it, and use `--allow-drop` last. The fixed recording path gives the same remedies.

`--allow-drop` states that the drop is intended. It is not a remedy for a refusal. The new cut event names each record as what it is, and the dropped members: `; previous cut <name> recorded <n> member(s); dropped: <members>`. A member that only the newest write held follows as `; dropped from <release>'s newest recorded write (an edit): <members>`. In a [stacked series](#stacked-series), a cut that does not start on the newest write's line adds `; not built on <release>'s newest recorded write (a cut) <commit>`. A cut on a machine that does not hold the newest write says `--allow-drop: cutting without holding it against <release>'s newest recorded write (a cut) <commit>, which this repository does not hold`, and its event adds `; not held against <release>'s newest recorded write (a cut) <commit>, which this repository does not hold`. A cut without the fix by hand of an `adopt` that the gate holds, of any release of the series, says `--allow-drop: cutting without the fix by hand of <release>'s adopt <commit>, in <n> file(s): <files>`, and its event adds `; without the fix by hand of <release>'s adopt <commit>, in <n> file(s): <files>`, once for each such adopt. Both name each file of the fix that the cut lacks. For a fix that this repository cannot measure, the line adds why and what held it, as the refusal does. For a fix whose files this repository cannot read whole, the cut says `--allow-drop: cutting without holding it against the fix by hand of <release>'s adopt <commit>, whose files this repository cannot read whole`, and its event adds `; not held against the fix by hand of <release>'s adopt <commit>, whose files this repository cannot read whole`. `<release>` is the release that the adopt recorded. Keep the reason and its dependency effects.

### Identical-cut exceptions

- When **every pin of the previous dated release is frozen**, or the previous dated release is **published**, a new later dated name can start identical, exit `0`. It says to `include`, `advance`, `drop` or `rebase` **before you push**. It is the composition to edit, not identical content to publish.
- A dated release is published when a tag names its local or publish-remote commit, or a `record: published …` note on the release names that commit in its evidence. Other `record:` rows do not count. `include`, `drop`, `advance` and `rebase` refuse a published release, exit `3`, and name what marks it: cut a new dated name first, then edit that.
- A fixed release has a **ledger-recording** path instead. It applies when the last cut event is missing or names a different commit than the published branch. Then `cut` audits that published composition, runs the composition and drop checks, and records that commit as the cut. It makes no commit and pushes nothing. Weak evidence can still give findings. When the ledger already records that commit, an identical cut is refused.
- A fixed release that was pushed by the fast-forward rebase has a carrier. The candidate leaves the carrier out, so it does not match the published commit. Neither the recording path nor the identical-cut refusal fires for it. Record such a commit with `adopt`, before the push ([Publishing](#publishing)).
- A member rewritten to the same content is a new parent, so it is a new composition. The comparison is with the published copy. An unpushed previous cut is not compared.

Cut and edit events keep full parent commits, every bookmark on them, and the commit and change id each wrote, in the [ledger](ledger.md). Use that evidence, not the current bookmark names, to find lost members.

## `knives release cut NAME --at REV`

Records a release cut outside knives as the recorded cut of NAME. REV is a revision that names one commit. Use it for a release that a person or a script merged by hand, such as a compose script's chain of merges. The command makes no commit, uses no temporary name and makes no throwaway cut. After it, `adopt`, the edit verbs and `audit` on each machine read the release as recorded.

The command holds the fork's lock from before the plan until the event is written, as every release write does ([above](#plan-and-keep-the-composition)). So two records of one name at once on one machine take turns, and the later one reads the earlier one's event at gate 4. A record on another machine reads that event after its ledger pull. The gates come in this order. Each refusal writes nothing and exits `3`, except where this list says otherwise:

1. NAME must be a dated cut of the series, in the grammar above, and a name that git can hold as a ref. Any other name is a usage error (exit `2`). `--at` on a fixed release branch is a usage error too: a plain `cut` records the fixed branch's published composition ([identical-cut exceptions](#identical-cut-exceptions)).
2. The plan must have no problems, and a shared ledger must pull, as for every cut.
3. REV must name one commit that shares history with the trunk: a commit other than the root is an ancestor of both. So the root commit, and a commit made on the root apart from the trunk, are refused. The commit must have no conflict (the refusal names the files), and it must not be a workspace's working copy (run `jj new` there first).
4. When the ledger already records a write of NAME, and the newest one is REV, the command writes nothing, says `is already recorded`, and exits with the plan's exit, which is `0` when the plan is clean. When the newest one is another commit, it refuses and names that commit: a commit made over a recorded write is recorded with `knives release adopt NAME`.
5. NAME must sort after every other release name of the series, locally and on the publish remote. It must also sort after every name that the ledger records a cut or edit of in the series. The refusal names the newer name. So record the older name first.
6. Each ref of NAME, locally and on the publish remote, must name REV. Otherwise the command refuses and names each ref and its commit. When no ref of NAME exists, the command makes the local bookmark NAME at REV. It moves no other bookmark.
7. When NAME is published (a tag or a `record: published` note names REV), the publish remote must hold NAME. Gate 6 has already put each ref of NAME at REV, so this gate refuses only a published NAME that the publish remote does not hold. Such a REV waits only for its push, so the refusal gives the commands that record it: `jj bookmark create NAME -r <REV>` when no ref of NAME exists, then `jj git push --remote <publish remote> --bookmark NAME`, then the same `knives release --repo <repo> [--series <series>] cut NAME --at <REV>`. It is not [the published remedy](#the-published-remedy), which is for a hand edit of a published release.

Then:

- **The members.** A parent that the trunk holds, which a trunk position reaches, is never a member. The event does not record it, and the audit replays it all the same. In a [stacked series](#stacked-series) with a previous release P, the members are the reading's: the side parents on the first-parent line of REV, never the literal parents of REV. P is no member, and the event records it first, under its label. A commit with one parent on that line refuses REV. A start commit, with P as its one parent, is a release with no member, and it is recorded. In any other series, the members are the parents of REV, carriers left out. REV must merge at least one member: a commit whose every parent the trunk holds, such as a one-commit branch on the trunk, is refused, saying that it merges no member. The previous release of the series, its newest other release locally or on the publish remote, is never a member either: a REV that merges it is refused and names it. A member that carries a merge past the trunk refuses the command: only a stacked series reads a release made as merges on its previous release. Outside a stacked series, these two refusals name the `stacked = true` setting on the series table; for the default series, which has no table, they say to record the release in a series that sets it. In a stacked series with no previous release on REV's first-parent line, REV reads as the series' first cut, which is flat, and the refusal says to rebase each member off the trunk.
- **The audit.** Each member, and each parent that the trunk holds, must replay empty onto REV, as in a cut: from its fork point with the trunk, or in a stacked series from its fork point with P. Nothing counts as carried forward, as in `members --verify`: a member that REV lacks, or whose lines REV changed, reads as missing. Then the audit measures the drift from the release that REV follows: P in a stacked series, else the newest other release of the series, as a cut's audit measures the release in hand. The series' first record follows no release, so the audit measures its drift from the fork point of its members with the trunk. Each later record measures its drift from the first record, so the first record gets the same check. A file that changed since that release or fork point, and that no member, no trunk parent and no trunk explains, refuses the command. The refusal names the file and what the audit measured it from: `the previous release`, or for the first record `the members' fork point with the trunk`. A file of a fix by hand that the gate holds is the gate's to check, not the audit's ([gates](#gates), 4).
- **The composition gate.** Then the command holds REV against the two events that a cut reads ([gates](#gates), 4), NAME aside: the event of the previous cut in the series, and the newest recorded write of the newest release that the ledger records a cut or edit of in the series. Gate 5 makes NAME sort after that release. Its newest write is its cut, its newest edit or an `adopt`, whichever the ledger records last. This repository must hold that write. Where it does not, as in a clone that has not fetched it, the command is refused, exit `3`: the refusal names the write, whether it is a cut or an edit, its commit and its release, and says to fetch, then record a commit that carries what that write carries; in a stacked series, to fetch, then build REV on it. It adds that, if the fetch does not bring that commit, `knives release adopt <release>` records the commit that this repository holds as the release's newest write. The members of that write are the members of its event: its evidence after the commit, without the parents that its parent set labels as the previous release or as a carrier. So a member that `include` added after the cut is held too, and so is each member of a stacked release, whose cut records no member. REV must carry each member of either event, as a cut must: the member is a parent of REV, an ancestor of a parent or of the base (P in a stacked series, else the fork point of the members with the trunk), a rewrite that stands for it, a commit with its tree, or its net diff is in REV's tree. A member of the previous cut that the newest write supersedes, with its change id, is not held. A member that REV does not carry refuses the command. The refusal names that release and each member of its newest write that REV does not carry, then the previous cut and each member that only it recorded. REV must also carry each fix by hand that the gate holds, as a cut must: the fix of each `adopt` of any release of the series, at each file where its hold has not ended, against the file's reference: the newest recorded write that holds the file with no conflict ([gates](#gates), 4). So a fix adopted on an earlier release, which later releases carried, is held at REV too, and so is a fix at a file that a later knives write left conflicted, with or without a conflicted cut between. REV's own tree must carry each such file: an adopt on REV's first-parent line carries nothing for the fix. A REV that holds a file that the fix deleted lacks the fix there. For a fix that this repository cannot measure, as in a clone that does not hold the adopt's commit, REV must hold at each such file what its reference holds there, and where the reference holds nothing at the file, REV must hold nothing there. Otherwise the refusal names each such adopt, its commit, the release that it recorded and each file of its fix that REV lacks, and for a fix that this repository cannot measure, that this repository does not hold the adopt's commit. It says to record a commit that carries that fix, or, to keep the new content of those files, to edit the release of the newest write by hand to hold it and run `knives release adopt <release>` for it. Where each file of a fix that REV lacks has no reference at all, as every recorded write leaves it conflicted, and the adopt's change does not change it, no commit carries that fix until an adopt gives those files a reference. So the refusal does not ask for a commit that carries that fix: it keeps the adopt remedy, which gives the reference, and `--allow-drop`. A file has no reference here where the walk for its reference stops at a recorded write that this repository does not hold, as each newer write leaves the file conflicted. Where the adopt's change does not change such a file, as for a fix that this repository cannot measure, REV lacks it whatever REV holds there. So where REV lacks a file with no reference here, the refusal names the fetch of that write first, with the remote and the branch or tag that has it now: `fetch <remote>'s <ref>, which holds <commit>, then record a commit that carries that fix`, and the adopt remedy follows. knives reads the branches and tags of origin, and of the publish remote where it is another remote, once each, with `git ls-remote`, only for a refusal that names such a fetch ([gates](#gates), 5). Where no remote has that write, no fetch brings it, so the file counts as one with no reference at all, and the adopt remedy stays the way on. Where a remote cannot be read, the last line ends `; <remote> could not be read`. Where this repository does not hold an adopt whose event's text does not read whole, it cannot read the files of that fix whole ([gates](#gates), 4), and REV is refused whatever it holds. Such a text is an older one that names the files in a list of more than 16 pieces, or follows its list of files resolved by hand with another part, so the list may end there or name a path that holds that part: it reads two ways. The refusal reads `it cannot be held against the fix by hand of <release>'s adopt <commit>: this repository does not hold <commit>, and the adopt's event is an older one that names the files of the fix in its text alone, in a list of more than 16 pieces, which may name a path of more pieces than this repository reads`, or ends ``in a list that `; why: ` follows, which may end there or name a path that holds it``, with the part that it found. Where a remote has a branch or tag at that adopt, its remedy names that fetch first, in the same words, then a commit that carries the fix, and gives no adopt remedy, as the fix names no file here. Where no remote that knives read has one, no fetch and no commit meets that fix, so the remedy asks for no commit for it. Its end below then adds why, and names only the remotes that knives read: `, as <remote> has no branch or tag at <commit>` where it read one, `, as neither origin nor <publish remote> has a branch or tag at <commit>` where it read both, and `, as no remote could be read for a branch or tag at <commit>` where it read none. Where this repository holds that adopt but cannot read it as a release of the series, the refusal reads `this repository cannot read <commit> as a release of the series` in place of the first reason. No fetch and no commit meets that fix, so the remedy asks for no commit for it. It gives the remedies of what else REV lacks, if any, then ends `re-run with --allow-drop to state the drop is intended: nothing in this repository can hold a release against the fix by hand of <release>'s adopt <commit>`. In each of these cases, the last line then ends `; --allow-drop is the last resort: it also waives the checks of each recorded member, of the newest recorded write and of each other fix by hand`. `--allow-drop` goes past that fix only by going past those checks too, the member checks included. So fetch the adopt first, where a remote has it, record a commit that carries the fix, and use `--allow-drop` last. In a stacked series, the newest write, or a commit that stands for it (a successor of it, or a commit with its tree, whatever its change id), must be REV or on REV's first-parent line ([stacked series](#stacked-series)). So a REV built on an older release than the newest recorded one is refused, whatever members it carries, and so is a REV built on the edit that an `adopt` replaced: the refusal names the write, whether it is a cut or an edit, its commit and its release, and says to build REV on that write. A REV built on a `jj duplicate` of the write is recorded. `--allow-drop` states an intended drop: the record then goes ahead. Its event names each record as what it is: the newest write first, as `; <release>'s newest recorded write (an edit) holds <n> member(s)`, then the dropped members, a member that only the previous cut held as `; dropped from previous cut <name>: <members>`, for a REV off that write's line `; not built on <release>'s newest recorded write (a cut) <commit>`, for a newest write that this repository does not hold `; not held against <release>'s newest recorded write (a cut) <commit>, which this repository does not hold`, and for each fix REV lacks `; without the fix by hand of <release>'s adopt <commit>, in <n> file(s): <files>`, with the files that REV lacks, or, for a fix whose files this repository cannot read whole, `; not held against the fix by hand of <release>'s adopt <commit>, whose files this repository cannot read whole`. A failed audit or gate records nothing.
- **The record.** The ledger gets one cut event, the event a knives cut writes, with `; recorded: composed outside knives` in its text. In a stacked series it records P under its label. It records the members, and never a parent that the trunk holds. It carries no `unchecked` mark. The event starts the background ledger sweep, so another machine reads the record after its next pull.
- The command prints one line: `recorded NAME at <commit> as its cut; nothing was committed`. When the publish remote does not hold NAME, the line ends with `; push NAME with jj git push --remote <publish remote> --bookmark NAME`. In each command that the command prints, NAME is one shell word: a name with a character other than `A-Za-z0-9._/+-` is in single quotes, and each `'` in it reads `'\''`.
- No orphan gate runs, because nothing is composed. No reap runs. Nothing is signed or pushed.

An example: series `9.2` has `stacked = true`, and a compose script made its releases 8.0.9 and 8.1. Record the older name first, then read the newer one back:

```bash
knives release --series 9.2 cut release/9.2/2026-11-15-speed-8.0.9 --at <commit of 8.0.9>
knives release --series 9.2 cut release/9.2/2026-11-17-speed-8.1 --at <commit of 8.1>
knives release --series 9.2 members release/9.2/2026-11-17-speed-8.1 --verify
```

8.1 is the chain `merge(merge(merge(P, D), M6), M5)`, where P is 8.0.9. Its event records 8.0.9 as the previous release and D, M6 and M5 as the members. An edit of 8.1 measures its own change against the merge of 8.0.9 and its members, so the edit keeps what each inner merge of the chain resolved. So does the check that reads 8.1 as recorded after jj rebases it over a member rewritten in place.

## Editing members

- **`include <branch> [--why "..."]`** adds one branch or revision as a parent. It does not move a member that grew, rebased (inside or outside jj) or merged upstream, which is `advance`. It refuses a second copy and explains the match. It refuses a tip that trunk already reaches, because that moves the base. Use `rebase` onto that trunk instead.
- **`drop <branch> --why "..."`** removes the parent, not the branch. A moved branch matches by ancestry or by the change id of the parent. For a rebuild outside jj, name the commit id of the parent. Removal never guesses from a reused name. `--why` is required and recorded on the release commit, and it must hold a reason. With no `--why`, or with one that is empty or only whitespace, it is a usage error (exit `2`) and writes nothing. When no other member's history carries the parent, the output after the write says `no remaining member carries <branch>'s content; the release loses it`, or, when the release's tree did not change, `<branch> left the parent set of <name>, and the release's content did not change`.
- **`advance [<branch>...] [--from <old-sha>]`** moves named branches exactly. Bare, it moves every member whose branch moved. Ancestry matches growth, and the change id past trunk matches a jj rewrite. Parents that trunk reaches have no unique successor, and `rebase` retires them.
- A named branch with no ancestry or change-id match can match by the `branch@commit` record of the last event. The output says so, because a reused name would move the member onto unrelated content.
- Bare advance refuses when one branch would replace more than one parent. A stacked integration branch does not prove that it replaced them. `--from` names the exact parent to replace and needs exactly one named branch. Use it when no record of the parent exists. Neither form advances onto a tip that trunk reaches.
- Each edit writes a new commit under the release name and abandons the commit it replaced, so no anonymous head stays, and says so. The old commit stays, with a note naming why, when another bookmark, a tag, a remote ref other than the release's own tracked ref on its publish remote, a workspace working copy on it or above it, or any other descendant rests on it. A working copy that sits on the release keeps it because rewriting that working copy would leave its workspace stale; the audit does not report it as an anonymous head while the working copy is there. Every later edit of the name, and the reap that forgets the name, also abandons each earlier commit the ledger records under it that is now a visible head nothing rests on (no publish-ref exception here), such as one left behind when that working copy moved on, and says so. An edit that leaves the release with conflicts abandons no earlier commit: they are the record of the last resolution, as with reap. The publish remote keeps the old commit until you push.
- In the same operation, every write (the cut, each edit, `rebase`, `adopt` and reap) also abandons each new head it leaves that nothing holds, when that head is an earlier write of the name or a commit whose newer version is still visible, and names each one. Nothing holds a head when no bookmark, workspace working copy or tag names it, and no remote ref other than the name's own tracked ref on its publish remote. So a carrier that a write leaves out stays hidden behind its publish ref. Any other head the write leaves, such as a member with no bookmark, stays visible for the audit to report. While the written release has conflicts, nothing is hidden.

## `knives release adopt [NAME] [--why TEXT]`

Records the commit a release name holds now as the name's newest knives write. Use it after you finish a release by hand: you resolved a conflict, renumbered a release log, repaired the composition on the release commit, or ran the fast-forward rebase before a push. With no `NAME`, it takes the release in hand of the selected series. It makes no commit and moves no bookmark.

- It pulls the ledger and reads the plan, as the edit verbs do. The commit is the local bookmark's. With no local bookmark, it fetches, then reads the publish remote's ref of the name.
- The write it replaces is the newest recorded write whose recorded parents, carriers left out, match the commit's parents, carriers left out. A parent matches when it is the recorded commit or a visible rewrite of it with the same change id. A recorded parent that this repository does not hold matches by commit id only. In a [stacked series](#stacked-series), the commit's members are the members that its reading gives, so the previous release is never one.
- The baseline is that write rebuilt on the commit's member parents: the tree a knives write onto them holds, with the release-log union, the tree that decides whether the release in hand is recorded ([below](#adopt-a-hand-resolution-before-the-next-write)). So a member rewritten in place, which makes jj rebase the release, is no change of the commit's own. A commit equal to an older recorded write is measured against that write itself. Where this repository does not hold the write, or the write's event carries the `; unchecked:` mark, the baseline is a fresh merge of the commit's member parents with the release-log union. The output names the baseline. In a stacked series, the write is rebuilt on the previous release and the members, and the fresh merge is a merge of the previous release and the members. The write's own change is measured against the merge of its own previous release and members, so a write made as a chain of merges keeps what each inner merge resolved.
- When the commit is the newest recorded write, or a copy of it with the same change id, parents and tree, `adopt` writes nothing and exits `0`. The exception is a newest write whose event carries the `; unchecked:` mark: `adopt` records the commit again, with no mark, and so ends the mark ([unchecked](#when-knives-cannot-check-the-release-in-hand)). A commit equal to an older recorded write is recorded as the newest, so the audit clears.
- Otherwise it abandons the earlier writes of the name that are visible heads nothing rests on, and records an `edited` event ([ledger](ledger.md)). Then it prints the adopted commit, the write it replaces and the baseline; the files resolved by hand; the files changed beyond the baseline's conflicts, with the reason; for each member and changed file, how many of the member's non-blank added lines, from its fork point with trunk, the commit does not hold; each carrier, labelled `<name> earlier write (carrier, not a member)`; one line for each `### ` heading that a release log's one `[Unreleased]` section holds more than once, as every write prints it ([above](#plan-and-keep-the-composition)), so a person who resolved a conflict and kept two `### Added` headings sees it; and each commit it abandoned. In a stacked series, it measures each member's added lines from its fork point with the previous release. So a member's deletion of the previous release's lines is no lost line, and the event records the previous release under its label.
- It exits `1` only against a recorded write, never against a fresh merge, and only for one of two losses: any of a member's added lines lost from a file that the baseline left without a conflict and that is not a release log, or none of the blocks a member added left in a release log or in a file that the baseline left conflicted. A block cut down there is the normal shape of a resolution: the counts report it, and the exit stays `0`. It records first. Read the counts, and repair the release if the resolution lost a member's change. A heading line that you renumbered is expected in the counts.
- A file that the commit changes and the baseline left without a conflict needs `--why`. Such a change is a repair, a restore or a renumber. Without `--why`, `adopt` refuses and names the files. The event keeps the reason. A `--why` must hold a reason: one that is empty or only whitespace is a usage error (exit `2`), and `adopt` reads and writes nothing.
- Every later cut and every later `cut --at` of the series must carry the adopt's fix, file by file: each file it resolved by hand and each file it changed beyond the baseline's conflicts, for as long as the file's reference still holds the adopt's content there. The reference of a file is the newest recorded write of the series that holds the file with no conflict ([gates](#gates), 4). So the next release must carry it, and every release after that one, whether a knives cut or a record. A write that keeps the fix, such as an `include` or a cut that carries the fix forward, does not end that. A knives write that leaves the file conflicted, such as an `advance` whose member changes the fixed lines, does not end it either, and a record after it must still carry the fix. A knives cut over that conflicted write goes ahead, exit `1`, names the fix as inconclusive at the file, and leaves the conflict for you: resolve it in place and run `adopt`, and keep the fix or replace it there. A cut that leaves the file conflicted where the newest write holds no conflict there is refused. A deletion is content: where the fix deleted a file, a release that holds that file lacks the fix. Where this repository can measure the fix, a member that changes other lines of a file whose lines the fix changed costs the fix nothing. There, a later write that removes the fix from a file, or changes its lines there again, such as a later adopt, ends the hold on that file alone, because its reference then no longer holds the adopt's content there. For a file that the fix deleted, that is a later write that holds the file again. The other files of the fix stay held. A cut or a record that `--allow-drop` lets go without the fix becomes the newest write, so the same holds for it, unless it leaves the file conflicted. A cut from a release bookmark that is still at the write the adopt replaced is refused, exit `3`, and names the adopt. A clone that does not hold the adopt's commit cannot measure the fix. It holds each file that the adopt's event names to what the file's reference holds there. Where the reference holds nothing at a file, the clone holds the fix there as an absence, until a later reference holds the file again. A cut or a record there must hold at each such file what its reference holds there, nothing included. Otherwise it is refused, exit `3`, and names the adopt's commit as one that the clone does not hold, and each such file. The event lists those files in `fix_files`, each path whole, beside its text ([ledger](ledger.md#automatic-entries)). An adopt event that an older knives wrote names them in its text alone, where a path that holds `, `, `; ` or ` (why: ` reads back in pieces. A reader joins the pieces back into each path that they may name. A clone that can measure the adopt holds only such a path that the adopt's own tree holds, beside the files that the adopt's change changes. A clone that cannot holds each such path: a path that the newest write does not hold is held as an absence, so a release that holds it is refused, names it and names `--allow-drop`, and one that holds none of them is not refused for them. A clone that cannot measure the adopt cannot read such a text whole where a list of it has more than 16 pieces, or where its list of files resolved by hand is followed by another part: the files changed beyond the conflicts, the reason that `--why` gave, the carriers or the added lines absent. That list may end at the part or name a path that holds it, so it reads two ways. There, every cut and every record is refused, exit `3`. The refusal names the adopt, says that its event is an older one that names the files in its text alone, and, for such a list, names the part that follows it. A clone that does not hold the adopt's commit is told first to fetch it, from the remote and the branch or tag that has it, then to cut or record a release that carries the fix. Where no remote that knives read has a branch or tag at that commit, as once an edit abandoned it and a later write moved the release's ref, no fetch brings it, so only `--allow-drop` goes on there. So it is in a clone that holds the commit but cannot read it as a release of the series: it has no fetch to make. Each such refusal ends saying that `--allow-drop` is the last resort: it also waives the checks of each recorded member, of the newest recorded write and of each other fix by hand, and for a cut of the commits reachable only from the previous release ([gates](#gates), 5).

It refuses, exit `3`, and writes nothing in these cases:

- The plan has problems, or a shared ledger did not pull.
- Upstream trunk does not resolve. Each member's added lines are counted from its fork point with trunk, and a stacked release is read down to trunk.
- The local bookmark is divergent. Or there is no local bookmark, and the publish remote holds no ref of the name after a fetch.
- The ledger records no cut or edit of the name. Cut it first. For a release cut outside knives, record it with `knives release cut <name> --at <commit>` ([`cut NAME --at REV`](#knives-release-cut-name---at-rev)).
- The commit still has conflicts (it names them), or it is a workspace's working copy (run `jj new` there first).
- A file outside the baseline's conflicts changed, and there is no `--why`.
- In a stacked series, a commit with one parent lies between the commit and its previous release. No member explains its change.
- Every parent of the commit is a carrier: you made the resolution as a commit on top of the release, or on top of `<name>@<remote>`. Such a release has no member, so no write can compose it. Every write refuses it too, also for a name with no recorded write. The remedy depends on the state:
  - A dated or series release that is published (a tag or a `record: published` note names its commit) gets [the published remedy](#the-published-remedy), whether or not the publish remote holds the commit. Its first step moves `<name>` to W, the recorded write that the resolution sits on.
  - Every other release gets the squash remedy. It starts `every parent of <name> is an earlier write:`. Where the name exists only as `<name>@<remote>`, its first step is `jj bookmark track <name>@<remote>`, because a squash moves only local bookmarks. Then squash the resolution into the release commit that it sits on: `jj squash --from <commit> --into <release commit> --use-destination-message`. That flag keeps the release commit's own description and opens no editor. The remedy adds `--ignore-immutable` after it when the publish remote holds that release commit. Then adopt. For a fixed release whose publish remote holds that release commit, the remedy also says to adopt again after the fast-forward rebase, before the push ([carriers](#plan-and-keep-the-composition)). For a name with no recorded write, the last step is to run the write again, because there is nothing to adopt against.
- No recorded write matches the commit's parents, carriers left out: the members changed outside knives. `adopt` prints this remedy:

  ```text
  <name>'s members differ from every recorded write; make the change with `knives release include`, `drop` or `advance` (a member added by hand: drop it, then include it); that write records the new composition, marked unchecked
  ```

  That `include`, `drop` or `advance` goes ahead and marks its ledger event `; unchecked: no match`. Then run `knives release adopt <name>`. It records the release and ends the mark ([unchecked](#when-knives-cannot-check-the-release-in-hand)).
- The release is published (a tag or a `record: published` note names its commit), and the publish remote does not hold the commit. `adopt` prints [the published remedy](#the-published-remedy).

A name of another series exits `2` and names the series that owns it.

### The published remedy

Consumers were given the commit of a published release, so a hand edit of it cannot be recorded under its name. You redo the edit under a new dated name. `adopt` and every write print this remedy as one line when a dated or series release is published (a tag or a `record: published` note names its commit) and the publish remote does not hold the hand edit, R. The publish remote holds R when its ref of the name is R or descends from R. A release whose every parent is a carrier gets this remedy whether or not the publish remote holds R. The line starts `<name> is published (<what marks it>), so a hand edit cannot be recorded under it:`. Then it gives these steps, in this order:

1. Move `<name>` back to its published commit, `<name>@<remote>`. When every parent of R is a carrier, move it to W instead: the recorded write that the resolution sits on, which is R's own carrier parent. Where a local `<name>` sits at R, the move needs `--allow-backwards`, and the step gives the command: `jj bookmark set <name> -r <commit> --allow-backwards`.
2. If the working copy is on R, or on an empty commit on R, move it off with `jj new 'trunk()'`. Never use `jj new <W>`: it leaves the working copy on a descendant of W.
3. Cut a new dated name. In two states this cut exits `1` once ([below](#the-new-cuts-expected-exit-1)).
4. Redo the edit on the new cut: `jj restore --from <R> --into <new name>`. Then adopt the new name: `knives release adopt <new name> --why '<what the edit does>'`.
5. Where the publish remote does not hold R: `jj abandon <R>`. The remedy gives this step only when nothing else rests on R: no descendant, no bookmark or tag other than `<name>`, and no working copy of another workspace. Otherwise it names what rests on R and stops there, because an abandon would rebase that work: `then stop: <R> is not to be abandoned, as <what keeps it>`. It then gives no abandon and no forget.
6. Last, `jj bookmark forget <name>`. Never use `jj bookmark delete`: a push carries a delete to the remote. The forget removes the local name and untracks the remote ref, so no later cut plans against the old name. Reap still reads the earlier writes of the name.

The remedy never moves the old name or its tag on the publish remote. When the published commit is R and rests on W, the new cut's reap keeps the old name without a finding ([reap](#knives-release-reap)). Audit then keeps one `release-drift` line on the old published name ([reports](reports.md#knives-audit-repo---all---no-github)).

#### The new cut's expected exit 1

In each of two states, the new cut of step 3 exits `1` once. The cut is still written. The finding is true at that moment, and the steps after the cut end it. The remedy gives the note for a state only in that state.

- `<name>@<remote>` names a commit other than the one that step 1 moved `<name>` to. This occurs, for example, when every parent of R is a carrier and the publish remote holds R. The cut prints `<name> names both <a> and <b>, and their trees differ (<n> files)`, with the two commits in either order. The remedy says `that cut exits 1 once`. The finding is true: the local name and its remote ref name two different trees. The forget in step 6 removes the local name and ends it.
- The publish remote does not hold R, and R is a visible descendant of the commit that step 1 moved `<name>` to. Only the old line reaches R, so the cut needs `--allow-drop`. The remedy names the flag and the commits that the cut must find: R first, then each commit that rests on R. The cut must print `--allow-drop: nothing dropped: the <n> commit(s) the cut does not carry are still visible: <commits>`, with exactly those commits. Its reap must print `kept <name>: it has descendants, whose heads are <heads>`. The keep is a finding because the publish remote does not hold R. The abandon in step 5 and the forget in step 6 end it. Any other `--allow-drop` answer, or any other commit in it, is a stop.

### Adopt a hand resolution before the next write

- The release in hand is **unrecorded** when its tree differs from the tree of its matched recorded write rebased onto the release's parents, carriers left out. In a [stacked series](#stacked-series), the write is rebased onto the previous release and the members, and the write's own change is measured against the merge of its own previous release and members, so a chain of merges keeps what its inner merges resolved. A jj rebase of that write, a fast-forward carrier copy and a metadata rewrite are recorded. A hand edit is not.
- A release equal to any recorded write of its name, or a copy of one with the same change id, parents and tree, is recorded.
- While the release in hand is unrecorded, `cut`, `include`, `drop`, `advance` and `rebase` refuse, exit `3`, and write nothing. The cut refuses whatever its audit would say. Each refusal names the remedy as a command: `knives release adopt <name>`. `adopt` asks for `--why` only for a change outside the conflicts.
- When knives cannot check the release in hand, the write goes ahead and says so ([below](#when-knives-cannot-check-the-release-in-hand)). `adopt` records such a release when this repository does not hold its matched write, or when that write's event carries the `; unchecked:` mark. It refuses one whose members match no recorded write: an `include`, `drop` or `advance` records that composition, and `adopt` then records the release ([adopt](#knives-release-adopt-name---why-text)). It refuses a name with no recorded write at all, which has no write to replace. `knives release cut <name> --at <commit>` records such a name as it stands ([`cut NAME --at REV`](#knives-release-cut-name---at-rev)). Otherwise the next write over it records the name, marked, and `adopt` then records it.
- A release whose every parent is a carrier makes every write refuse, with the remedy that `adopt` prints ([adopt](#knives-release-adopt-name---why-text)). An unrecorded published release that the publish remote does not hold gets [the published remedy](#the-published-remedy).
- A release whose name has no recorded write at all is not refused, unless its every parent is a carrier. So a fork whose ledger predates knives is not blocked. Each write over it goes ahead marked `; unchecked: no record` ([below](#when-knives-cannot-check-the-release-in-hand)).
- After a hand restore of a release (`jj restore --from <commit> --into <name> <path>...`), run `knives release adopt <name> --why '<what was restored and why>'`, then cut.

### When knives cannot check the release in hand

knives cannot check the release in hand against its recorded writes in three cases. In the first, this repository does not hold the matched write: another machine made it, and nobody fetched it here. In the second, no recorded write matches the release's parents, carriers left out: the members changed outside knives. In the third, the ledger records no write of the name: a release older than the ledger, or one made without knives. Then `cut`, `include`, `drop`, `advance` and `rebase` do not refuse. The exception is a release whose every parent is a carrier, which every write refuses ([adopt](#knives-release-adopt-name---why-text)). Each other write goes ahead. A cut still runs its composition gate, which refuses when this repository does not hold the newest recorded write of the series ([gates](#gates), 5). Before it writes, it prints one of these lines, after the repository's name:

```text
knives could not check <name> at <commit> against its recorded writes: the recorded write its members match, the recorded <cut|edit> <id>, is not in this repository; knives did not fetch; `knives release adopt <name>` records it
knives could not check <name> at <commit> against its recorded writes: its members match no recorded write, so they changed outside knives; knives did not fetch; make the change with `knives release include`, `drop` or `advance` (a member added by hand: drop it, then include it); that write records the new composition, marked unchecked
knives could not check <name> at <commit> against its recorded writes: the ledger records no write of the name; knives did not fetch; a write over it is marked unchecked until `knives release adopt` records the name it writes
```

- The write's ledger event ends with `; unchecked: W absent`, `; unchecked: no match` or `; unchecked: no record` ([ledger](ledger.md#automatic-entries)). `audit` shows a note while that write is the newest write of the name ([reports](reports.md#knives-audit-repo---all---no-github)). So no later pod reads the release as measured.
- The mark is sticky. The release stays unchecked while the event of the recorded write that it equals or matches carries the mark. A hand edit over such a write is unchecked too, not refused. Each write over it marks its own event with the same reason, and prints:

  ```text
  knives could not check <name> at <commit> against its recorded writes: the release in hand is unchecked since the recorded <cut|edit> <id> (<reason>); knives did not fetch; `knives release adopt <name>` records it
  ```

- `knives release adopt <name>` ends the mark. Its event carries no mark. Nothing measured the marked write, so `adopt` measures the release against a fresh merge of its members.

### Why `adopt` beside the recording paths

The fixed scheme's cut records a published commit that the ledger lacks (the recording path above). `cut NAME --at REV` records a release cut outside knives under a dated or series name ([above](#knives-release-cut-name---at-rev)). `adopt` is still needed:

- `cut NAME --at REV` records only a name that the ledger records no write of. `adopt` records a commit made over a recorded write: a resolution, a renumbered log or a repair.
- The fixed recording path records only what the publish remote holds. `adopt` records a resolution before it is pushed.
- For a fixed release, `adopt` records a name that this repository holds only as the publish remote's ref. For a dated or series name with no recorded write, `cut NAME --at REV` records such a name too.
- A fixed release pushed by the fast-forward rebase has a carrier. The candidate leaves the carrier out, so it no longer matches the published commit. The recording path and its "nothing to cut" refusal do not fire for it. `adopt` is how it is recorded.

## `knives release rebase [REF]`

- In a [stacked series](#stacked-series), `rebase` refuses, exit `3`, and moves nothing. Each release is built on the previous release, so there is no base to move. `include` or `advance` a member that you rebased by hand instead.
- Moves members and the release merge onto the target. Member bookmarks and workspaces follow, and recorded resolutions replay. Every other release name that is pushed or published stays on its commit, and the output says so. One never pushed follows its rewrite, also said. It does not authorize a broad raw rebase.
- Bare, it targets the first upstream trunk commit that holds the merge commits of all our PRs that **merged, not closed**. With none merged, there is no default, so give a commit.
- A merge commit missing from local trunk refuses until `sync`. An outdated knives immutability rule refuses before any move and names `start <branch>` to refresh it.
- Pushed or published earlier releases keep their names and commit ids, and every tag stays where it was. The rebase's copies of them that nothing rests on are abandoned together and reported. A copy stays when a bookmark, a workspace working copy, or a descendant outside the set rests on it. A note says why. Copies stacked only on each other go together.
- After a bare rebase, also a no-op, members with merged PRs and no work past the target are removed, with the reason recorded. `--no-drop` keeps them. A branch with later work stays and says so.
- An unheld stale parent refuses, exit `3`. The refusal names its continuing branch and `advance`, or `drop` when none continues. A legacy trunk parent is shed, because base is not membership.
- When every member merged, rebase refuses to leave trunk as the only parent. A drop of the last parent also refuses. Reap the composition or include new work.

## `knives release reap`

Forgets superseded dated refs locally and on tracking remotes, then abandons their merges. It also runs after a dated cut. **No remote repository changes.** A fetch can bring tracking refs back. Standalone `reap` prints one JSON or TOON document (`repo`, `reaped`, `forgotten_only`, `kept`, `notes`, `abandoned_earlier`) under `--json` or for an agent; the reap inside a cut prints prose with the cut.

- Superseded means "not the newest name of this series", in the one order of [Names and consumer gates](#names-and-consumer-gates). So a later name on one date retires an earlier one, and a labelled name is read like any other. A name the series cannot read has no place in the order, and the reap never takes it.
- In a [stacked series](#stacked-series), a superseded name whose commit the live release descends from loses its refs, locally and on tracking remotes. Its commit stays, and the reap abandons nothing of it, its earlier writes included. This is also true while the live cut has conflicts: the commit stays as the resolution record. The output says `reaped <name> (refs forgotten everywhere; commit kept, <live> descends from it)`, and the exit is `0`. A superseded name that the live release does not descend from keeps the rules below. So such a name on another line stays, with exit `1`, while a branch rests on it, and that finding is true.
- Otherwise, while the live cut has unresolved conflicts, every superseded cut stays as the resolution record.
- A cut pinned outside release refs (a tag, an untracked remote bookmark, a local bookmark of another name such as `keep/…`) has its refs forgotten and its commit kept, with the pin named. Exit `0`, which is normal for a tagged or retained release.
- A superseded cut that something rests on stays untouched, its refs too, and the output names what rests on it. Exit `1`, except for the quiet keep below. That is a workspace working copy on it or above it, empty or not, or any other descendant, on the cut, on a commit an edit wrote under its name, or on a rewrite of either: the rule an edit uses to keep the commit it replaced. Abandoning the cut would rewrite each of them onto the cut's parents, which can leave a working copy's workspace stale and make it a conflicted merge. A cut made from the workspace that sits on the previous cut keeps that cut too. Move your own empty working copy (`jj new <live cut>`, which drops it), then run `knives release reap`. A working copy with changes stays a descendant until it is rebased off the cut. Another workspace's working copy is its owner's to move.
- The quiet keep: a superseded name kept only for what that name published exits `0`, and the output still has its `kept <name>` line. Two conditions must be true. Every descendant of the name's ref commits and earlier writes is reachable from the name's own ref on the publish remote, or from a tag on one of those commits or descendants. And nothing else names any of those descendants: no workspace working copy, no local bookmark, no other remote bookmark and no other ref. The name's own local bookmark does not count. The old name after [the published remedy](#the-published-remedy) is kept so: consumers were given what it published, and the new cut redoes it. This rule applies to `knives release reap` and to the reap after a cut. Every other keep exits `1`.

## `knives release members`

```text
knives release members [REF] [--verify]
knives release members [REF] --carries REV
knives release members --census [--no-github]
```

- Bare: direct parents, commits, holding bookmarks, and branch tips advanced past them. `REF` picks another release. In a [stacked series](#stacked-series), the previous release has a row of its own, `<P> previous release (not a member)`, and the member rows are the members that the release's reading gives.
- `--verify` replays each member into the release, one replay per member. In a stacked series, each member replays from its fork point with the previous release. Problems exit `3`, missing or unexplained content `1`, else `0`.
- `--carries REV` asks whether the net content of the revision is carried. With a target, it checks only that target. Without one, it checks live releases and upstream trunk, then superseded cuts.
- `--census` asks the deletion-safety question for every maintained branch. `--no-github` is valid only with `--census`, and the orphan test is then unknown. It does not combine with `REF`, `--verify` or `--carries`.

The verdicts are those in the main skill: `carried-exact`, `carried-rewritten`, `carried-rebased`, `NOT carried`, `conflicted`. An explicit target exits `0` for any carried verdict, `1` for not carried or conflicted, `3` when unresolved or uncheckable. A superseded target can say carried, but the untargeted safety question still needs a live release or upstream trunk. Neither grep nor absence from bare `members` answers deletion or rebase safety.

## Publishing

Release commands never push. Publish a new release name with `jj git push --remote <publish-remote> --bookmark <name>`.

A release that the publish remote moves only forward (a fixed release branch) needs a fast-forward. A knives write does not descend from the published head, so git refuses a plain push of it. Rebase it onto the published head, adopt it, then push the commit:

```sh
jj git fetch --remote <publish-remote>                                   # read the published head as it is now
old=$(jj log -r '<name>@<publish-remote>' --no-graph -T commit_id)     # the published head
pre=$(jj log -r <name> --no-graph -T commit_id)                         # the write knives made
jj rebase -r <name> -d <parent-1> -d <parent-2> -d "$old"               # each parent as its own -d, in the release's order, then the published head
jj restore --from "$pre" --into <name>                                   # the rebase can add the published head's content; put the write's tree back
JJ_USER='<author>' JJ_EMAIL='<email>' jj metaedit --update-author <name> # only when the author must change
knives release adopt <name> --why "fast-forward of $pre onto the published head $old"
git push <publish-remote> "$(jj log -r <name> --no-graph -T commit_id):refs/heads/<name>"
```

- Run `adopt` after the last rewrite, the author change included, and before the push. The publish ref still names the old head then, so the old head reads as a carrier, and the ledger's newest write is the commit that the push publishes.
- Change the release commit's author only with `jj metaedit`. It keeps jj's `change-id` header in the git commit. Git plumbing drops that header, and a fresh pod then cannot read the pushed copy as a carrier by its change id.
- Push with no `+` and no `--force`. Stop when git refuses. Never use `jj git push` here: it moves the remote branch whenever the branch is still where jj last fetched it, as `git push --force-with-lease` does, so it hides the non-fast-forward refusal that is this branch's only backstop.
- `adopt` writes a ledger entry, which starts the background sweep, and the sweep pushes a shared ledger by itself. So when git then refuses the push, the ledger holds a recorded write that the fork does not hold. Nothing in the ledger says that the fork published it. The next pod starts from the published head, which an earlier `adopt` recorded, so its edits are not refused. Its cut is refused until it holds the newest recorded write ([gates](#gates), 5): an `adopt` of the published head, or its first edit, records a write that it holds. The refusal says to fetch, and, if the fetch does not bring that write, to run `knives release adopt <release>`. Here no fetch brings it, because the fork never received it, so that `adopt` records the published head that the pod holds as the newest write. Its audit reports `release-drift` against the newest recorded write, which it lacks, until its first write or an `adopt`.
- Without the `adopt` step, nothing records the pushed head. When the head's parents match a recorded write that the next pod does not hold, that pod cannot check the head. Its first edit goes ahead, prints the unchecked line and marks its event `; unchecked: W absent` ([unchecked](#when-knives-cannot-check-the-release-in-hand)). A cut there is refused while that write is the newest recorded write, because the pod does not hold it ([gates](#gates), 5). One `adopt` records the head. After two pushes in a row without `adopt`, a fresh pod that holds neither recorded write still reads the older pushed copy as a carrier by its change id. So the head matches the newer write, which that pod does not hold, and an edit goes ahead unchecked in the same way. `adopt` records it.
