# Maintaining fork pull requests and releases

You own the requested outcome, not just the dispatched PRs. A PR-only request ends with verified PR maintenance; a request to address upstream debt or make releases good also requires release and consumer verification below. Respect explicit exclusions such as no deployment. Do not turn a PR-only request into a release or deployment change.

## 1. Start with `knives notch`, not a new document

**`knives notch` is the existing read/write record of this work. Read it before deciding, dispatching, or repairing.** It holds prior decisions, maintainer promises, rejections, release changes and verification evidence. There is no separate estate document to find or create, and no Markdown inventory to maintain beside knives.

Use the requested repositories, mapped through `knives repos` and the registry at `~/.config/knives/repos.toml`. An existing project skill can identify a library family and its consumer-specific requirements; it does not replace the live records. The registry name and upstream slug are different identifiers: take the slug from the entry's `upstream` URL, stripping `.git`.

Read these in order, substituting names from the preceding output:

```sh
knives repos
knives status <repo>
knives notch --repo <repo>
knives release --repo <repo> members
knives notch <release> --repo <repo>
knives notch <branch> --repo <repo>
knives notch --pr <number> --repo <repo>
```

Bare `notch` gives recent context (the newest 20 human notes and an event summary), not every branch's history. Named branch/release reads give the full chronology; `--pr` also finds records across a PR's former branches. Read all relevant chains. Older notes without this workflow's prefixes remain valid context: never discard them as invisible. Check timestamps, anchors and evidence against the current head; a note on an earlier tip may have been superseded. A recorded requirement still matters even if a later release lost its implementation. Use `knives notch --verify <subject> --repo <repo>` to check recorded anchors/evidence, then investigate discrepancies rather than treating an old assertion as current proof.

**For direct reading, run the command examples above as written: no `--json`.** Looking up
branch, commit or evidence fields, saving a capture, and preparing a JSON final report are
still direct reading. The model interpreting output is a reader, not an executed JSON parser.

Request `--json` only when the bytes feed executed code doing a real filter, count, join or
other programmatic operation that needs JSON. Keep that consumer with the command evidence.
`jq .`, parse-and-reprint wrappers, or a filename ending in `.json` do not create that need;
do not invent a parser step just to justify the flag. Save native output unchanged for records
you will read yourself.

Default machine output and JSON carry the same data; JSON does not defeat a harness's
line/output truncation. Recover the complete captured output or page its saved form when
truncated. Do not conclude from an elision or change serialization merely to read it yourself.

`fork-work` governs workspace entry; `using-knives` governs command semantics; `using-jj` governs version control. Read upstream contribution files and workflows for current gates and requirements. Read relevant project guidance for consumer wiring. Put new branch/release decisions in `knives notch`, not in another document.

**Done when:** requested repo identities are known and their relevant notch histories have been read, with inherited obligations distinguished from stale assertions.

## 2. Account for release members and open PRs

The maintained population is the **union of release members and open PR branches**, not only the open PRs. An open PR outside the release is still maintained; a release member without a PR is still accounted for; an overlapping branch is counted once as a work item but keeps both identities. Deduplicate PR aliases by upstream slug and PR number, and identify release-only members by the release parent commit. When a release parent, branch tip and PR head differ, keep all three revisions in the row; that is a composition gap to resolve, not a duplicate to collapse.

Use the current `knives status <repo>`, `knives release --repo <repo> members`, `knives audit <repo>` and, for consumer state, `knives consumers <repo>`. Reconcile open-head discrepancies the audit reports before claiming complete coverage. Read the corresponding notch chains before classifying any member. A merged or closed PR does not by itself prove that a release no longer needs its delta.

`status` exit 1 means findings; exit 3 or `problems` means unanswered data. A missing checkout, unconsulted forge, unreadable record, or incomplete page is not zero work. Keep counts provisional and investigate the missing source; proceed on complete independent repos while repairing the gap. A search result is corroboration, not a substitute for the registry and release membership. Repositories outside the requested set are listed once and not dispatched.

Create one scratch directory outside workspaces and `/tmp`, `~/.cache/knives-sweep/<unique-run>/`, with one `<repo>/pr-<number>/` directory per PR and a separate `<repo>/release/` directory. Include a run-unique suffix, not just the date. Save pre/post command output, diffs, drafts and gate logs there in their native formats; name the paths in dispatches and reports. Scratch is working material; notches and published PRs are the record.

The report starts with `Population: <p> open PRs and <r> release-only members, <u> distinct work items across <n> requested forks; coverage complete|incomplete (<timestamp>)`. State every incomplete source. A PR-only request labels release-only items outside its repair scope; it does not claim they were verified.

**Done when:** every union member is accounted for, all counts cite saved output, and missing observations are explicit rather than silently filtered away.

## 3. Dispatch one owner per PR

One `maintaining-fork-pr` owner per PR, end to end. Dispatch batches of at most eight and keep at most eight active PR owners. Observe every start's claim or refusal before filling the next batch; claim-lock waits are normal. Release a worker slot on handback, but retain responsibility for the PR until merge or explicit reassignment.

**An owner runs on a strong model, never the harness's default fast/cheap subagent tier.** Owning a PR is judgment work — reading a maintainer's question and forming a position, deciding which stale text would actually mislead and which is harmless, recognizing that a `decision:` in the chain already answers today's question. A fast model works the steps as a checklist and produces exactly the failure this skill exists to prevent: correcting replies nobody needed, resolved threads reopened, settled decisions re-escalated. If the harness's generic task agent maps to a fast tier (check its model-role configuration before the first dispatch), select an agent type or model override that runs a strong model, and say which in the dispatch record. The fresh-context reviewer in step 4 has the same requirement. Only read-only recon that will be re-judged by an owner may run on a fast tier.

A claim held by someone outside this sweep is respected: report its `why` text and continue independent work. Do not infer death from a quiet `seen` field. If an owner stops unexpectedly, establish its state through coordination and the existing claim/workspace, then use the supported claim-recovery procedure before taking over. Never blindly force a claim or restore the shared jj operation log.

Each dispatch contains, in order:

1. The whole shipped `maintaining-fork-pr` skill.
2. Registry repo name, upstream slug, PR number/URL, branch, and its current status row, in the format already captured. For a PR whose branch is a release member, also include the release member row and parent commit. The owner obtains the authoritative PR head from the forge and reports the original PR head, expected branch/bookmark head and candidate head as separate revisions.
3. The relevant **`knives notch` history**, including inherited promises, decisions, release membership evidence and unresolved obligations. Supply complete captured entries or a readable saved path; do not replace them with your summary. The owner refreshes them before acting.
4. Relevant upstream/project guidance, its source paths, and any recorded publication constraints. The owner derives exact gates from current repository files; there is no prerequisite per-repo document. Supply the registry's configured `forbidden` terms and applicable existing outbound-prose rules. If none are configured, say so; do not invent a list. An empty configured list is not a privacy waiver.
5. The whole shipped `pr-preflight` skill, your reviewer-relay address, and the **per-PR** scratch path.
6. The branch's `placement:` notch or a statement that none exists. If proposing upstream-bound work yourself, complete `fork-work`'s challenge before dispatching.

The orchestrator handles release-only members under the same claim, evidence and independent-review discipline, without inventing PR numbers or opening PRs to satisfy the inventory. A named branch is claimed before anyone edits it; an anonymous member is carried, dropped or classified by release evidence and `knives notch` records, not by fabricating a branch. A bounded branch implementation can be delegated to one owner only when the requested scope already authorizes that work. Classify with evidence: supplied upstream, still proposed upstream, downstream configuration, or obsolete. Record the reason and disposition with `knives notch <branch> -m ... --evidence ...` when a branch exists, or on the release/repo subject for anonymous members. Do not automatically include an open PR in a release, and do not treat a branch with no upstream PR yet as exempt from needing one.

**Done when:** every open PR has one owner or a named reason it cannot be worked, and every release-only item has an owner/disposition appropriate to the requested scope.

## 4. Review, record, and coordinate integration

### Reviewer relay

When an owner sends its packet path, check the packet's repo/PR identity, original PR head, expected branch/bookmark head and candidate head against the dispatch. Dispatch a fresh-context reviewer with the packet unedited and this verdict contract: `PASS (no repairs)`, `PASS per fix (k/k)`, or `FAIL: fix|body|drift|placement`, with evidence for every question. The reviewer independently examines the **whole PR diff**, not just the owner's finding list, even when recon found nothing.

Reject an owner packet whose PR evidence is only a first page or truncated capture. Comments, reviews, review threads, check runs and workflow runs must be complete for the PR head being judged, or the missing page is an unanswered source and the owner returns to recon. A `null` thread count, elided saved output, or bounded `first:100` result with more pages available is not a clean review input.

Reject packets missing the `placement:` notch or substituting approval/tests for evidence; return them to recon.

Relay the verdict verbatim within 20 minutes; do not substitute your judgment or soften a FAIL. A malformed verdict is returned to the reviewer for correction. The owner waits 30 minutes, then records `decision: reviewer verdict outstanding; repair commits <ids>; bookmark not moved` and hands back. That timeout is your work, not a decision for the human: obtain the verdict and resume the owner at verification with the original PR head, expected branch/bookmark head and candidate commits preserved.

### Notches are the handback record

Read, do not merely request, each owner's records:

```sh
knives notch <branch> --repo <repo>
knives status <repo>
```

New entries use `placement:`, `recon:`, `rehome:`, `repair:`, `record:`, `verify:`, `decision:` and `handback:`, each with `--evidence`. Preserve and read older formats. A `handback:` plus released claim ends the worker's active ownership, not the overall task. Accept a thread disposition only with evidence: `-> <commit>`, `declined: <reason>`, or `already answered <reply-url>`. Record outstanding promises explicitly, with the reply URL, rather than counting them as fulfilled. Verify new replies actually published before reporting them as addressed.

### Decisions that reach the human

You are the last filter before a question reaches the maintainer of record, and you own the same judgment `maintaining-fork-pr` asks of an owner. Before forwarding any `decision:` an owner wrote:

- Read the branch's whole chain yourself. If an earlier note answers it, the decision is closed: write a `decision:` notch quoting that note, re-dispatch the owner with the answer, and never show the human the question. One PR carried the same A-or-B question through four owners over three weeks because each orchestrator forwarded the newest `decision:` without reading the one dated before it.
- Read the maintainer's words yourself, not the owner's summary of them. A summary that says "declined the CIDR ask" for a thread that actually said "you introduced a second system, please unify" sends the human a question about the wrong thing and takes several rounds to unwind. When you put a maintainer's ask in front of the human, quote it.
- Bring a position. The human gets: what was asked (quoted), what the record says, what you would do and why, what changes under the alternative — in the repository's own terms, with every identifier expanded on first use. A bare `#1075` or a fork's internal vocabulary is not a question the human can answer.
- A question about the PR's design or scope is not a decision for the human unless it needs authority you lack (money, an upstream commitment, removing something the human asked for). Confidence you lack is your work to do, not theirs.

Record the human's ruling as a `decision:` notch on the branch, in full — the reasoning, not just the verdict — so no later owner can re-open it by reading only the prefix. A ruling that establishes a standing rule (for example, "infra PRs bake in the upstream's defaults and our settings live in our own configuration") is also recorded on the repository subject with `knives notch --repo <repo>`, where every future dispatch reads it.

### Single writer and release-wide changes

Ordinary branch writes belong to its claim holder. Owners append repair commits; they do not rewrite shared ancestry. A lone branch's necessary rebase follows `fork-work`; a release-member rebase belongs to the orchestrator. The release claim is the write lease for release refs and release-wide mutations, not permission to push an owner's PR head. Stop admitting owners for that repo, wait until **every affected member claim is released**, hold the release claim while integrating, and recheck the no-claim barrier immediately before the write; if a new external claim appears, back off instead of racing it. An unrelated repo can continue.

```sh
knives release --repo <repo> members
knives status <repo>
knives release --repo <repo> rebase [<target>]
```

Choose the target from the actual need; bare rebase uses the documented merged-PR target and may require an explicit target. Record `rehome:` with the target and resulting release commit. Exit 0 is not enough: confirm each affected member is actually on the target, its patch survived and its commits are conflict-free. A member still on the old base is unresolved work. Resume verification for **all affected PR heads**, not just the owner that requested the rebase; never push their rewritten heads without their claims and fresh verification, and keep the original PR head, expected bookmark head and candidate head distinct in the re-dispatch.

Use the existing release plan and `knives release --repo <repo> members <release> --verify` to check current parents and content carriage. Also check target ancestry explicitly for each member with `jj -R <checkout> --ignore-working-copy log -r '<target> ~ ::<member-commit>' --no-graph` (empty means the target is an ancestor), and check each member's conflicts. Content carriage or the release merge containing the target does not prove every member moved onto it.

**A member with no conflict left is not yet a member that works.** A rebase onto a trunk that moved modules or reordered events breaks members in files no conflict marks. The 2026-09-22 oh-my-pi rehome onto v18.2.9 found three such shapes, none of them visible in the rebase: an import of a module upstream had moved (only `bun check` saw the TS2307), `new FileSessionStorage()` defaults upstream had added after the member's cutover (found by reading upstream's new call sites while porting — a semantic mismatch with the new trunk that no hunk showed, fixed on the member, not the release commit), and a member's streaming test whose history snapshot upstream's event ordering had moved (that member's rebase had conflicted in its CHANGELOG only, its own checks were deferred, and the break escaped to the composed-release gate). Type-check every member at its rebased tip, run its own tests there, and audit the trunk's new call sites against whatever the member cut over — the conflicted members and the clean ones alike — before declaring the rehome resolved.

If an external actor moves a branch under an owner, inspect old-to-new content. Trunk-context-only movement can be ruled on by the orchestrator, with the original head, chosen new head and reparented candidate commits recorded. Resume the owner to re-review/re-test the resulting candidate before pushing. A conflict with the user's intent requires a real decision; do not guess or reuse a verdict for a different tree.

**Done when:** each packet has a verdict, each handback has been checked against notches and current state, and every integration mutation has one owner and preserved-content evidence.

## 5. Finish release and consumer verification

Run this phase when the request includes releases, upstream debt or consumption. PR-only scope does not authorize release edits or deployment.

1. **Reconcile intended content.** Read the release and member notches again, the release plan, the content census and consumers:
   ```sh
   knives release --repo <repo>
   knives release --repo <repo> members --census
   knives consumers <repo>
   ```
   For each maintained delta, record whether the intended release must carry it, inherits it upstream, deliberately excludes it, or needs repair. Use `members <target> --carries <revision>` for content carriage; an upstream PR's merged state or a source-text match alone is not proof. A conflicted probe needs investigation, not an automatic drop.
2. **Compose the intended release.** Use the existing `release advance`, `include`, `drop --why`, `rebase` and `cut` commands as documented in `using-knives`, under the integration barrier. Advance repaired members to verified heads. Include an unreleased PR only when it is intended and ready to ship. Read actual consumer pin constraints before choosing an in-place edit or a new cut: a consumer frozen on an older release is still behind but does not block editing the current release, while a tool refusal that every pin of the release being edited is frozen on a revision means an in-place edit would reach nobody and the answer is a new cut, not a parallel lineage or forced ref move. Keep required old refs reachable. Do not generate an identical release just to have a new name.

   **Classify every member before composing it, and write the classification into the release notch.** Each member is exactly one of: `upstream-PR <url>` (an open or merged upstream pull request carries it); `upstream-pending, placement <notch anchor or commit>` (its `placement:` notch and commit body record the UPSTREAM verdict with the defect or capability gap it fixes and the evidence — a reproduction or red→green test — that its upstream PR is opening from); or `neither`. `neither` blocks: the member is dropped (`drop --why`) or returned to its author, not composed. Neither valid classification waits on the upstream PR's state: an `upstream-pending` member ships in the release the moment the release is gated and published (step 5), and the consumer pins that release without waiting for the PR to be opened, reviewed or merged (the time to start using a fork change is the time to make it — Sami, 2026-09-25). The classification is disclosure, written into the release notch and the pin PR's delta; it is not a gate on shipping. The release owner applies `fork-work`'s ownership test here a second time — *if the fork were replaced by upstream main tomorrow, would anyone but us miss this?* — because the consumer repository is where its deployment's operating policy lives (lifetimes and reaping of jobs, caps, quotas, schedules, alerting), and a fork member is for a defect in the library's own machinery or a capability nothing outside the library can provide. There is no third classification: a policy-shaped member that only looks like it belongs in the fork is either a missing library capability — UPSTREAM, with its PR opening as part of the same work — or it is CONSUMER and does not belong here at all; `neither` is what a member gets when it is CONSUMER work mistakenly composed as a fork member, not a policy exception. The case: a fixed creation-time lifetime cap on every job was composed into a release with no classification; it carried no `placement:` notch and no path upstream, cited a ruling it did not implement, and the owner had it dropped — the same behavior was a scheduled job in the consumer's own cluster. `maintaining-inspect` owns the consumer's record of the incident and the deployment state; read it before claiming that a fork-side drop has reached a consumer.

   **A drop is swept from the leaving parent's net diff, not from its member's heading.** Every parent that leaves the candidate — a `drop --why`, a member the cut's composition gate names (before `--allow-drop` accepts it), a parent of an old release that a rebuild does not re-include — is swept against `<candidate>`, the composition in hand once that parent is out, before it is cut or published; a parent leaves unless some parent of the candidate is it, carries its change id, or carries its first line. The unit is that parent's **net diff from what it shares with the candidate**, never its commits one at a time: `jj -R <checkout> --ignore-working-copy diff --from '<fork>' --to <parent> --git`, `<fork>` being `heads(::<parent> & ::<candidate>)`. That is the parent's own fork point — never a newer upstream head, and never the old release's other parents, which would let content that reached the release through two leaving parents look carried by each from the other's side and vanish from both diffs — moved up to any commit of its series that a staying member is stacked on, so that a line the series added and later removed, which that member puts back, shows as a removal the candidate still holds. `--from` takes one revision; where `<fork>` names several (a merge-based upstream, say), diff from their merge, built in git's object store and not as a jj commit, because the sweep is a read: `git --git-dir="$(jj -R <checkout> git root)" merge-tree --write-tree <head1> <head2>` prints the merged tree's id on its first line and writes no jj operation and no ref (exit 1 only means a path conflicts, which the tree holds with conflict markers and is read by hand), `git --git-dir=… diff <tree> <parent>` is the net diff with repo-relative paths, `git --git-dir=… show <tree>:<path>` is the fork's copy of a path, and a third head merges onto `git --git-dir=… commit-tree <tree> -p <head1> -p <head2> -m fork`, a commit no ref names. One head chosen by hand lets the others' history into the diff. A scratch jj merge is a head in every agent's `jj log` until it is abandoned, a crash or a concurrent rewrite leaves it behind (`abandon <commit id>` after a rewrite prints "No revisions to abandon" and exits 0), and `knives audit` never reports it, because its orphan revset skips an empty undescribed commit; knives' own probes stopped writing in order to read for the same reason (#18). Judging the commits one at a time judges intermediate states the series itself rewrote, and upstream squash-merges, so every review fix-up inside a leaving series is one: composing one fork's `release/2026-09-25`, the 36 commits behind dropped parent `4428b3f0` hold 306 hunks and add `"ForAnyValue:StringEquals"` — a line the very next commit, the fix-up `b78a1625`, replaced with `ForAllValues` plus a `Null` guard, and that no upstream commit ever had, so per commit it has no supplier and reads as a loss whose restore puts back the looser IAM condition the series itself tightened. That parent's net diff is 75 hunks, holds no `ForAnyValue` line at all, and still adds every `middleman_model_discovery_profile` line, which is the real loss. Keep the commit list for citations: `jj -R <checkout> --ignore-working-copy log -r '<candidate>..<parent>' --no-graph`. Sweep only the `heads()` of the leaving commits and the advanced members' old commits (below) taken together, and sweep as leaving only the leaving commits among them: the previous release carried a descendant's state, which is that one's net diff, so leaving out its ancestor loses nothing that release had — even where the descendant removed the ancestor's content, as `5b6ab0ab` removes all of `17cf130b`'s `auth anthropic-token` CLI command and so has an empty net diff. Such a removal takes one row naming the commit that made it, because a consumer still pinned to an older release that carried the ancestor loses the content on this pin; the count pass below, run on each non-head's net diff with the head it sits under in the candidate's place, prints exactly the lines that row covers. The heads of the leaving set alone are not enough: a leaving commit that an advanced member descends from is then swept twice, the second time at a state the series itself rewrote — three of the old-release merge's leaving parents here, `c206e797`, `038554c9` and `70d1e837`, sit under advanced members, and as heads they add 153 hunks and 1467 lines, 25 of whose 44 residue lines the series rewrote before the old release carried it. Sweep a leaving **old-release merge** as all of its parents — each without a successor as a leaving parent, each with one as an advanced member at the commit the merge carried — and as its own delta, content only that merge commit carries, on every path it touches: `jj diff -r <merge>` on a path its parents merge without conflict, and on a conflicted one, whose `-` side holds conflict markers, the resolution's own lines, taken as added lines: the lines of the merge's copy that no parent's copy holds, `grep -vxFf parents merge` with every parent's copy of the path in `parents` and the merge's in `merge`. Here that is 42 parents, 29 leaving and 13 advanced, against a 179-commit range, and a delta of 53 paths: the 7 conflict-free ones come to 12 hunks with 12 residue lines, and the 46 conflicted ones hold 72 resolution lines no parent has, 59 of which the count pass prints — one is `infra/app.py:306`'s `model_discovery_profile=config.middleman_model_discovery_profile,`, the case's own loss at the place the published restore put it. The old release commit's own delta is swept the same way: here 25 of its 26 paths are conflicted, and the count pass prints 96 of their resolution lines. **An advanced member is swept too**, at the commit the old release carried and not at its new tip, because no other check in the cut looks at that commit; its net diff is read exactly the same way, and it is cheap — this cut's 24 advanced members, 11 among the old release's own parents and the 13 inside its old-release merge, came to 451 hunks and 7223 changed lines, of which the mechanical pass below left 236 lines to read.

   **Every line of that diff gets a verdict, in a `record:` notch row naming its path and the line numbers the diff prints for it.** Run the diffs from the checkout root so the rows hold repo-relative paths (`--name-only` for the paths, the same command with `-- 'root:"<path>"'` for one path's hunks); through `-R` from another directory jj prints each path relative to the caller's cwd, `../../../src/<fork>/infra/__main__.py`, a row no other directory can read. The verdicts are `carried` and `on trunk` — **the candidate holds the line at that path, as many copies of it as the parent holds, or, where it holds fewer, this copy where the parent has it, which the merge below decides** — and the row cites those candidate lines by number and the commit that introduced them there. Supply is the candidate's content, never the cited commit's own diff: read it from `jj --ignore-working-copy file annotate -r <candidate> -T 'commit.commit_id().short() ++ " " ++ line_number ++ ": " ++ content' <path>`, which names the commit per line — a commit id, because a change id can be divergent, and a plain repo-relative path, because `file annotate` refuses `root:"..."`. The two readings disagree, and the other one is unsound — `358ef368` adds `"sts:IdentityTokenAudience": "https://api.anthropic.com"`, so by its own diff it "supplies" a line `45f60d50` later replaced and the candidate does not have, which is the silent loss this sweep exists to catch. A line the candidate lacks can still be `carried` or `on trunk` **by replacement**: the row names the candidate lines that now do its job, each with the commit that introduced them, and may cite several commits, from upstream or from another member. A replacement counts only when every name the line defines or reads has a successor among the named lines (`AwsRoleProfile` → `AnthropicStsWifProfile`, `duration_seconds` → `_STS_TOKEN_DURATION_SECONDS`); a neighbour in the same hunk doing a different job is not one, and a name with no successor is the part that is lost. Matching names says nothing about values: a replacement row states each value it changes — a default, a limit, an audience, a version — and when the replacing line is an advanced member's successor, the change is also production behavior that step 5's pin PR discloses. `54597092`, rebuilt for this cut from `61538f54`, one of the 13 advanced parents above, moves the default of `karpenter_node_pool_cpu_values` from `["2", "4", "32"]` to `["2", "4", "8", "16", "32"]`, and the case's audience line below is replaced by a tuple that adds a second audience. "Superseded" and "landed upstream" are this verdict, with the replacing lines cited, never a reason for `dropped`. `dropped` cites the notch or ruling that intends the revert — the one behind the commit that wrote the line, which `file annotate -r <parent>` names, since a composition parent speaks only for the composition — or a search of each consumer's pinned revision showing nothing uses what the line did, and that search is not a literal name match in the consumer's source: "uses" includes use through a configuration key or keyword the consumer sets and the fork's own code reads. Searched literally here, the discovery hunk's own identifiers (`MIDDLEMAN_MODEL_DISCOVERY_PROFILE`, `load_anthropic_model_names`) appear nowhere in agent-c's `meta/` and only in a test docstring under `platform/`, while the capability is in use: the consumer's cluster component and its production stack module both pass `middleman_model_discovery_profile`. A **removed** line the candidate still has needs a verdict too — say why the deletion is not needed (the candidate's own copy does that job) or it is a loss of a deletion. A line with none of these verdicts is a loss to restore, however much of its path or hunk is settled, and the restore goes by block and is merged, not typed. A **block** is the removed and added lines the diff prints between two context lines, and every block holding a line the count pass below prints goes back whole, its settled lines with it — before the first loss, between two and after the last — because a count settles a line on a copy the candidate gained anywhere in the file, so a settled line beside a loss is as likely a fragment of the lost code as one the candidate kept, and a restore without it parses and does the job of neither the parent nor the candidate: `da80cef5`'s `importer/eval/converter.py` restored without its `else:` (`:51`, settled on the candidate's `:92`, the `else:` of an `if results:` above it) records `plan` as the agent of a `plan` plan and raises `UnboundLocalError` for every other, and `34971307`'s `processors/eval.py` without its `raise` (`:198`, settled on the candidate's submit-failure handler at `:72`) answers that the object exists for a 403, an `AccessDenied` or a `SlowDown`. Where each copy sits is the merge's question, not the reader's: put every block of the parent's copy that holds no printed line back to its fork side, merge the result onto the candidate's copy with `git merge-file -p cand fork restore` — the candidate's copy of the path, the fork's (`file show -r <fork>`) and that result, three plain files and no repository — and rule on what it lands and on each conflict. A line the candidate already holds where its block goes comes out once and is `carried` at that candidate line: the `RolePolicy` block below merges to the candidate's own 29 lines and one conflict, the literal audience against its replacement, and of `9c3f1952`'s five `_auth: HumanApiAuthDep,` in `api/human_server.py`, all printed against the candidate's two, two merge away and three conflict with the candidate's `auth: HumanApiAuthDep,`. A place the candidate rewrote comes back as a conflict, read by hand with the restore's side as the lost block; a run of four or more lines both sides share, with a letter or digit among them, comes out between two conflicts of that place, shown once though each side needs it, and `git merge-file --diff3` shows the place whole. The restore keeps whatever no row covers. A two-way `diff` of the parent's copy against the candidate's is not that test: it pairs lines by text alone, so where the candidate wrote code of its own at a block's place it pairs the lost block's boilerplate with the candidate's, and `34971307`'s restored tests lose their fixture parameters, their `):` and the `await eval_processor._process_eval_set_file(...)` they exist to check. A block with no printed line stays out: the count carries it, wherever its copies sit. The restore is a member of its own, classified like any other, never a drop. Where the candidate now does that work somewhere else the restore goes there — `4428b3f0`'s `infra/__main__.py` kwarg belongs in `infra/app.py`, where the published restore `7ce7a791` put it.

   **Settle mechanically first and read only the residue, or the sweep will not be done at all.** `members <candidate> --carries <commit>` settles a row only when it says carried: it measures the commit's whole tree from its common ancestor with the target, so an earlier commit that conflicts or is missing makes the ones after it probe the same way, and this per-line reading is what step 1's "needs investigation" means for a conflicted probe. For everything else the pass counts **copies**, per path, in the parent and in the candidate: `jj --ignore-working-copy file show -r <candidate> 'root:"<path>"' > cand` and the same with `-r <parent>` into `par`; `comm -23 <(sort par) <(sort cand) > fewer` lists, copy for copy, the lines the candidate holds fewer of than the parent, and `comm -13 <(sort par) <(sort cand) > more` the lines it holds more of; then the path's diff piped through `sed -n '/^@@/,$s/^+//p' | grep -xFf fewer` prints every added copy of a line the candidate is short of, and through `sed -n '/^@@/,$s/^-//p' | grep -xFf more` every removed copy of a line it holds extra; which copies are the short ones is the merge's call above. Presence is not a count, and settling on it is the source-text match step 1 says is not proof: a line found anywhere in the file settles, so the case's discovery block in `middleman/src/middleman/models.py` settles its two lost `else:` branches on unrelated `else:` lines at candidate `:571` and `:713`, and restoring what printed yields valid Python in which a configured profile still needs the stored key and no profile sends no key at all. Counted, both `else:` lines print, and the published restore has both. Everything those two commands do not print is settled, and its row cites the candidate lines it settled on — except in a block that also holds a printed line, which goes to the merge whole, because a count balances a lost line against a copy the candidate gained anywhere and only the merge says where each copy sits. For a path the candidate no longer has, find where the content went — `jj --ignore-working-copy log -r '::<candidate>' -n 1 -- 'root:"<path>"'` names the change that removed it and `--summary` on that change names what it added — then run the pass against that path; the move itself is the row's replacement. Adjacent residue lines doing one job take one row, split wherever a name has no successor. Rule first on the added residue naming an identifier absent from the whole candidate tree and on every removed residue line, which is where a real loss hides; a lost deletion names only what the candidate still has, so no ordering by name ever reaches it. A lockfile hunk is read per package, not per line: it is settled when the candidate's lock is current for its own manifests (`uv lock --check` in an export of the candidate, for a uv lock) and resolves every package the parent's lock names at the same version or a later one; a package it lacks or resolves older is the residue, since a lock-only upgrade is content no manifest line shows. The size is why all of this is mechanical: this cut's 19 leaving parents expand to 47 leaving commits and 39 heads, whose net diffs hold 1072 hunks and 23957 non-blank changed lines; the count pass settles 20322 of those lines and leaves 3635 residue lines in 298 hunks — 512 naming one of 238 identifiers the candidate does not have anywhere, 290 removed lines it still holds, and 38 of the hunks in lockfiles — and on the 149 paths with a printed line that the candidate still has, the 339 blocks holding one come to 6825 lines, of which the merge lands 1377 cleanly and leaves 209 conflicts in 111 paths, before any row is written. **The sweep is finished when every line the passes print or the merge lands has its `record:` row** — per path, the lines the passes print, the lines the merge lands or leaves in a conflict, and the lines each non-head's pass prints against the head it sits under, less the lines the rows name, print nothing. A row per path is not that check, since one row per path passes having ruled on nothing, and a path list is not either: the non-heads' lines sit on paths no swept diff need list, as 895 of `17cf130b`'s do on 6 paths under `5b6ab0ab`'s empty diff, of 1233 across this cut's eight non-heads. A drop whose sweep is not finished is not made: keep the parent, or its rebuild, in the candidate. The parent's heading is never the fallback: the member-level answers — `drop`'s note that nothing remaining carries the parent, `--why`, `--allow-drop`, a quiet orphan gate (it asks only whether commits stay reachable, and every parent of the previous release still is) — say nothing about the content behind a parent, and a member's own content can be genuinely superseded while a line that reaches the release only through it is not.

   The case: composing one fork's `release/2026-09-25`, the owner dropped `feat/middleman-aws-role-identity` (`4428b3f0`), and `5463935b` among the parents of an old release the cut rebuilt, as superseded — their aws_sts feature had landed upstream and its file, `middleman/src/middleman/anthropic_wif.py`, had been renamed to `credential_broker.py`. That held for the aws_sts half, and the net diff shows it holding: in `4428b3f0`'s net diff the `aws.iam.RolePolicy` block settles 29 of its 30 lines by count, on the candidate's own copy of the block at `infra/core/middleman.py:457-486`, which trunk's `358ef368` introduced, and its one residue line — the literal audience — is replaced by `45f60d50`'s shared tuple at `:38` and at `:475`, inside that block; the renamed module's `class AwsRoleProfile` and its whole STS token leg are replaced line for line by `credential_broker.py`'s `AnthropicStsWifProfile` (`:390`, over `_BaseStsWifProfile` at `:378`) and `_fetch_sts_jwt` (`:838`), and `b78a1625`'s rewrite never appears, because the net diff carries only the condition the series ended with. What was not superseded is in the same diff: `StackConfig.middleman_model_discovery_profile` and middleman's `MIDDLEMAN_MODEL_DISCOVERY_PROFILE` discovery auth, whose upstream port was still an open pull request. `infra/lib/config.py` is three hunks, each adding a `middleman_sts_web_identity_enabled` line and directly after it a `middleman_model_discovery_profile` line; `358ef368` introduced the STS line the candidate has, and neither trunk nor the candidate has any discovery line, so in every one of the three the STS line settles and the discovery line beside it is a loss — ruled per path or per hunk, `config.py` reads `on trunk` on `358ef368`, and a restore built from what is left over still lacks the field whose absence is step 3's TypeError. The recon had listed `b2b04566` and `74587d44` by name — the two commits the restore's record names as how the previous release carried the capability, both inside `4428b3f0`'s net diff — and ruled on them inside a five-commit group under the feature's heading, "drop, superseded on target", citing upstream commits for the feature and none for any line of any of them; the plan written for that cut already had a per-commit rule, and it was weighed for the two tips a reviewer had named, never for the content behind them. A rule applied only where someone pointed is a patch, not a rule. Step 3 has how the loss was caught and what it would have broken.
3. **Verify the composed candidate.** Run its complete applicable gates and exercise the changed public surface on the candidate itself. Check every member and integration resolution, and run the **resolution-delta guard**: a recorded conflict resolution is carried forward by every later `cut`, `advance` and `rebase` (each rebuilds the release by duplicating it onto the new parent set), so a resolution that restored a whole file from one parent becomes a permanent, silent revert of every other parent's content in that file — on 2026-09-16 one fork release shipped 163 upstream files at month-old content through nine iterations this way, with no conflict and no record. Before publishing, build the fresh automerge of the release's parents and require the release's diff from it to be a subset of the paths that genuinely conflict:
   ```sh
   jj new '<release>-' -m guard                                   # fresh automerge of the release's parents
   jj diff --from @ --to <release> --name-only | sort > delta      # the recorded resolution delta
   jj resolve -r @ --list | awk '{print $1}' | sort > conflicted   # the paths that genuinely conflict
   comm -23 delta conflicted                                       # must print nothing, or only recorded semantic conflicts
   jj abandon @                                                    # drop the guard commit
   ```
   Any path the guard prints is a file the release changed without a conflict to justify it; put the automerge's content back (`jj restore --from <guard> --into <release> <path>`) and re-resolve only the conflicted paths, hunk by hunk. Never resolve a release conflict by `jj restore --from <one parent>` of a whole file. One kind of unconflicted change belongs on the release commit: a **semantic conflict**, where two members merge cleanly but the composition fails a gate (a test stub typed against one member's signature, which another member widened). Fix it on the release commit, not on a member — a member stays correct standalone and must not depend on a sibling — and record it in the release notch by path, the two members whose composition needs it, the gate error, and the hunk verbatim, with `jj diff --from <guard> --to <release> -- <path>` byte-equal to that hunk. Every path the guard prints that is not recorded this way is a defect. For a pure restructure, require tree identity with the verified reference; otherwise account for the exact intended delta. Then run **absolute consumer capability contracts**: a capability lost before the preceding release will escape a previous-cut comparison, and so will one this cut loses through a drop its owner judged intended, because every structural comparison — the cut's member audit, its composition gate, the guard above — takes a stated drop as the delta it was told to expect. The `release/2026-09-25` drop in step 2 took `StackConfig.middleman_model_discovery_profile` with it; agent-c's cluster component always passes that keyword and both live stacks use the capability (`caller-discovery-<stack>`), so pinning the candidate would have raised a TypeError in every agent-c Pulumi run that builds that cluster, staging and production included. Find a consumer's contract tests by searching its test trees for the pinned package's own name and for the symbols the pin exposes, which turns up both halves: the static tests that build the consumer's components against the pin, and the post-deploy live tests (here under `platform/`) that exercise the capability at runtime. The live half needs a deployment, so before publish it checks the candidate only on a dev stack deployed from it, and otherwise it checks the pin after publishing; the static half caught this one before publish, and the live half, run on such a stack, is what would have caught the discovery authentication the same drop took. agent-c's pinned-capability contract tests, run with the candidate substituted for the pin (a `file://` pin, relocked), caught it before publish — the one gate that night to find a defect the review rounds, oracle passes and thermonuclear reviews had not. Read historical requirements in `knives notch`; a previously lost required capability is a defect to fix, not a baseline to accept.

   **Judge the candidate's test failures against a control, not against zero.** A full suite on a developer box fails for reasons that are not the release: ambient cloud credentials, terminal variables, the user's own plugins, load. Run the same command on a pristine export of the target trunk — one the suite can actually run in, in the same environment, and not a workspace of the managed fork (for example `git archive <target> | tar -x` into a fresh directory with its dependencies installed) — and diff the failure sets by test name, not by file label: a suite runner that chunks files reattributes a failure to a different chunk label when members add test files. A candidate-only name counts once it reproduces in isolation on the candidate and not on the control; when its test file does not exist on the control (a member added it), judge it on the candidate alone, where failing deterministically in isolation means a regression. A scrubbed-environment re-run of the candidate (`env -i` with no ambient credentials and a plain `TERM`) is a cheaper first cut at "environment or release?". On the 2026-09-22 v18.2.9 rehome, the first gate's 54 raw failure lines — 43 distinct test names — reduced to exactly one member regression this way (the streaming test above, whose test file the member adds); the rest failed identically on pristine v18.2.9, passed in isolation on both sides, or did not recur in the next gate run.
4. **Verify the consumer chain.** Identify authoritative consumer trunk pins, resolved lock commits, build inputs, submodule/binary artifacts and any intermediate package that injects its own dependencies. A consumer's direct package pin does not necessarily control a runner's independently installed version. Verify the full relevant chain against the intended candidate. Use existing project deployment/verification guidance for the real surface, not an upstream's unrelated dev environment. Local gates, a changed lockfile, a published branch and deployed behavior are distinct evidence.
5. **Publish and consume deliberately.** A local cut or in-place release edit is not published; a published ref is not consumed unless the authoritative consumer resolves it. Publish the verified release to the registry's publish remote (`release`, otherwise `origin`), verify the remote ref with `knives pushed`, and complete the consumer pin/build/deployment steps required by the user's goal. Do not deploy when explicitly excluded or bypass credentials/approvals. Verify the final resolved and, where required, running revision and exercise the intended behavior there. Re-run verification after a relevant change. Record `record:` and `verify:` on the release with exact candidate, published and consumed commits plus gate/runtime evidence.

   **The consumer's pin PR discloses the delta.** A pin-bump PR body states every production behavior change the pin carries, in plain numbers, under `## Production behavior delta`: per member the new release adds or moves, what production does differently after the pin, upstream-pending members marked as such; `none` is written out when nothing changes. Disclosure, so the reviewer sees the policy, not a gate. Supply it from the classification above — the pin's author reads the release members and their notches, not the release title. The pin PR behind the lifetime-cap case in step 2 listed "lifetime cap" and named neither the number nor that only one deployment carried it; that omission is what the section exists to prevent.

If publication or consumption cannot proceed because of a real external prerequisite, complete independent work, record the exact blocker and report that stage **blocked**, not ready with a follow-up. Do not ask the human to ratify ordinary membership, naming, rehome or backward-compatible repair judgments already within the task; consult evidence and prior notches and decide. Ask only for missing authority, a genuine change in direction, or a conflict with the user's stated intent.

**Done when:** intended content is verified in the release and at the requested consumer/runtime boundary, or the unmet boundary is explicitly blocked with evidence. A PR push alone cannot satisfy this phase.

## 6. Report verified outcomes, not just completed accounting

Assemble the report from the saved live observations and the **`knives notch` chains**. Refresh the population for PRs that moved/merged during the sweep; reconcile changes rather than silently losing a row. Every original item retains a disposition. All newly discovered in-scope obligations are accounted for.

Per PR: maintainer asks, each repair/disposition and its commit/reply evidence, verification on the exact head, unresolved threads, remaining forbidden hits with reasons, and genuine blockers. Per release-only member: its ownership/disposition, carriage evidence and verification, without pretending a PR review occurred. Per requested release: intended composition, candidate/published/consumed revisions, absolute capability and runtime evidence, and any unmet boundary.

Use separate statuses: **accounted for**, **verified**, **published**, **consumed**, **blocked**. A handback or complete inventory proves only accounting. A decision note is not a repair. Never report a skipped gate, an unstarted workflow or a unit suite as successful end-to-end verification.

For every PR, keep the census line:

`<repo>#<n>: CI <head-specific run conclusions/pending> / review comments <unresolved, dispositions> / thermonuclear <fresh-context verdict> / e2e <actual surface evidence or not run> / forbidden <remaining hits>`

Each cell cites a notch or saved observation. For every requested release add:

`<repo>/<release>: composition <verified|blocked> / published <revision|not published> / consumers <resolved revisions|blocked> / runtime <evidence|not run>`

Executable pending CI remains owned after owner handback and watched through a real background watcher/event subscription; refresh on completion and repair failures before calling the PR verified. Approval-gated `action_required` stays **unrun**: reproduce the applicable job locally, retain the limitation, and never ask maintainers to approve workflows. Continue independent work while an item waits. Existing upstream PRs remain owned after handback; release verification is independent of waiting for an upstream merge.

Do not open unsolicited PRs/issues, route around credential gates, or change shared/global configuration to get a gate green. The evidence and the user's requested boundary, not the number of handbacks, determine completion.
